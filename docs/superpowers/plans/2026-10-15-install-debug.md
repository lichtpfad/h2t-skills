# Install debug

Цель: каждый слой установки на каждой целевой платформе доказан одной командой, каждый
найденный дефект имеет issue и тест, а повторение ловит CI. Результат проб становится
функциями `check()` wizard'а (`docs/superpowers/specs/2026-10-14-setup-wizard.md`), так что
работа не делается дважды.

Повод: три установки подряд прошли плохо — внешний пользователь (macOS, Codex,
2026-10-14), второй ноутбук автора (Windows, Claude Code, 2026-10-15), и сама первая
оценка «готов к раздаче», сделанная по тестам, а не по пути пользователя.

## 0. Идеальная установка — путь пользователя

То, к чему ведёт этот план. Каждая строка — проверяемое свойство, а не пожелание.

1. Человек говорит агенту «установи h2t» или запускает одну команду сам. **Никто не
   клонирует репозиторий**: ни один канал установки не требует чекаута, `git clone` нужен
   только для разработки пака.
2. Плагины ставятся командами, которые может выполнить агент:
   `claude plugin marketplace add lichtpfad/h2t-skills --json` →
   `claude plugin install h2t-core@lichtpfad --scope user --json` (и `h2t-ops`);
   в Codex — `codex plugin marketplace add lichtpfad/h2t-skills@<sha>` → `codex plugin add …`.
   Слэш-команды — форма для человека, а не единственная форма.
3. CLI ставится одной строкой из закреплённого коммита:
   `uv tool install "git+https://github.com/lichtpfad/h2t-skills.git@<sha>"`. uv сам кладёт
   исходники в свой кэш — это не клон в рабочую папку.
4. Сразу после установки — ни одной ошибки хуков ни на одной платформе, ни на одном
   сообщении. Внешних утилит, кроме `uv` и харнесса, не требуется.
5. Человек выбирает нужные коннекторы; каждый выбранный настраивается по тексту из
   программы, секреты не идут через чат, интерактивные шаги делает человек.
6. Готовность доказывает одна команда (`h2t-ops doctor --install`), а не слова агента.
7. Обновление — явная команда, которая доводит до диска и плагины, и CLI с зависимостями.

Пункты 1–4 и 6 исправляются в этом плане; 5 и 7 — wizard'ом.

## 1. Эталон — как установка должна работать

Восемь слоёв. Слой исправен, только если исправны все слои под ним; дебаг идёт снизу вверх.

| Слой | Контракт: что значит «работает» | Чем доказывается |
|---|---|---|
| **L0 Предпосылки** | есть `uv`; есть харнесс (`claude` и/или `codex`); на Windows — Git Bash, которым харнесс запускает хуки; Python ≥ 3.11 находится резолвером `resolve-h2t-python.sh`; **никаких** других внешних утилит (сейчас нарушено: `jq`) | `command -v`, запуск резолвера, версия |
| **L1 Плагины** | marketplace добавлен; h2t-core и h2t-ops установлены и включены; в кэше лежит версия из `marketplace.json` текущего коммита; скиллы видны агенту | `claude plugin list --json` / `codex plugin list`; каталог кэша; список скиллов в живой сессии |
| **L2 CLI** | пакет `h2t-ops` в `uv tool`, 9 команд на PATH; **все зависимости импортируются** (версия `0.2.1` не меняется и ничего не доказывает); источник — закреплённый коммит или editable-чекаут, и это известно | `uv tool list`; импорт зависимостей интерпретатором инструмента; `h2t-ops --version` (источник) |
| **L3 Хуки** | все 11 записей `hooks.json` отрабатывают на каждой платформе: молча при успехе, без ошибки в TUI; `inject-h2t-context` даёт `<h2t-context>`; `gather-on-skill` / `gather-on-prompt` дают `BRIEFING:` | синтетический payload на stdin каждого обработчика → код выхода и stderr; живая сессия |
| **L4 Конфиг** | `~/.h2t/config` существует или его отсутствие безвредно; имя машины закреплено (`H2T_MACHINE_NAME` в `settings.json`) | `setup_h2t.py doctor --json` |
| **L5 Секреты и коннекторы** | у каждого секрета одно место записи; каждый выбранный коннектор проходит живой запрос на чтение; невыбранный не считается ошибкой | `connectors-check --live`; поиск ключа по всем местам чтения |
| **L6 Жизненный цикл** | `session-start` показывает брифинг; `handoff` пишет запись в корень сессий этой машины | запуск обоих в чистом проекте; файл на диске |
| **L7 Обновление** | обновление плагинов и CLI доходит до диска; новые зависимости ставятся; ничего не обновляется без явной команды | версия в кэше, импорт новой зависимости, `uv tool list` |

## 4. Правила дебага

1. **Состояние, а не отчёт.** Агент, команда установки и пользователь могут сказать «готово» — считается только проба.
2. **Сначала позитивный контроль.** Каждая проба сначала проходит на заведомо исправной машине (автора), иначе «не найдено» и «сломан инструмент» неразличимы.
3. **Одна гипотеза — одна проба.** Никаких цепочек правок вслепую; на чужой машине — только однострочные команды без heredoc (R4).
4. **Область называется до запуска.** Какая платформа, какой слой, какие файлы.
5. **Секреты не печатаются.** Только наличие, длина, хеш (`.claude/rules/secrets.md`).
6. **Каждый дефект заканчивается тестом или issue.** Тест виден красным до исправления.
7. **Наблюдение пользователя — данные, объяснение агента — гипотеза.** Агенту `3dwalker` и агенту на ноутбуке верим в том, что они видели, и проверяем то, что они вывели.

## 5. Фазы

### A. Инструмент пробы — `h2t-ops doctor --install`

Одна команда, только чтение, JSON по слоям L0–L7: для каждого слоя `ok | fail | skip`,
причина и следующая команда. Это будущие `check()` wizard'а; модуль `h2t_ops/setup/checks/`.

- L0: `uv`, харнессы, Git Bash на Windows, результат резолвера Python, **наличие внешних утилит, от которых зависят хуки** (сейчас `jq`).
- L1: список плагинов харнесса, версия в кэше против `marketplace.json`.
- L2: 9 команд, импорт каждой зависимости из `pyproject.toml` интерпретатором инструмента, источник (editable / git@sha).
- L3: каждый обработчик `hooks.json` получает синтетический payload; ожидаются код 0 и пустой stderr.
- L4–L5: как `setup_h2t.py doctor` / `connectors-check`, плюс **все места, где найден каждый ключ** (D3).
- L6: `h2t-gather --briefing-only` в пустом проекте.
- L7: сравнение закреплённого коммита с установленным.

Готово, когда: тесты на каждый слой видны красными на подставленной поломке; на машине
автора (P1) все слои `ok` — позитивный контроль.

|---|---|---|
| P1 | новый пользователь macOS на ноутбуке | удалить пользователя |

### C. Прогон матрицы

На каждой платформе, строго по README, без подсказок агента:

1. `h2t-ops doctor --install --json` до установки (ожидается: L0 частично, остальное `fail`).
2. Установка по шагам README; после каждого шага — снова проба, вывод сохраняется в файл.
3. Каждый `fail` → строка в реестре §3 → issue (через `h2t-core:report-issue` на чужой машине, напрямую на своей).

Порядок: P3 (самые свежие отказы) → P1 → P2 → P4.

### D. Исправления по слоям, снизу вверх

| Порядок | Дефекты | Направление |
|---|---|---|
| 0 | D20 | README и `h2t-core:setup`: агентские формы установки плагинов, CLI только из `git+…@<sha>`, явный запрет клонирования; «из чекаута» — в раздел Development |
| 1 | D1 | убрать `jq` из обработчиков: JSON разбирается Python-резолвером или чистым bash; тест запускает каждый обработчик с PATH без `jq` |
| 2 | D8, D9 | после пробы: если хук наш — исправить; замер Stop-хуков на Windows, при секундах — кэш интерпретатора |
| 3 | D5, D6 | версия CLI из коммита сборки; L2-проба проверяет импорт зависимостей; README и setup: после обновления зависимостей — `uv tool install --reinstall` |
| 4 | D2 | `utf-8-sig` для всех JSON-конфигов коннекторов; понятная `ConfigError` при невалидном JSON |
| 5 | D3, D4 | сначала `decision.yml` (единое место, миграция, срок отказа от старых путей), потом код |
| 6 | D7 | проба в Codex на P2; при отказе — абсолютный путь к скрипту от `h2t-ops` |
| 7 | D11–D16 | в рамках wizard'а |

Каждое исправление: тест красный → исправление → тест зелёный → проба на затронутой платформе.

### E. Регрессионный гейт в CI

- job на `windows-latest` и `ubuntu-latest`: установка пакета в чистый HOME, `doctor --install` для L0–L3, все обработчики хуков с синтетическим payload **и PATH без `jq`** (есть ли `jq` в образах раннеров — не измерено; job первой строкой печатает `command -v jq` и затем убирает его из PATH, иначе гейт не поймает D1);
- импорт всех зависимостей из окружения `uv tool`.

### F. Передача в wizard

Модуль проб из фазы A становится `check()` шагов wizard'а; реестр §3 — его тестовые случаи.

## 6. Критерии выхода

1. P1–P4: чистый пользователь проходит установку по README, `doctor --install` — все слои `ok`.
2. Ни одной ошибки хука в TUI за сессию на P1 и P3.
3. Каждая строка реестра — либо «исправлено» с тестом, либо issue со ссылкой.
4. CI-гейт фазы E зелёный и виден красным на подставленном `jq`-зависимом обработчике.

## 7. Вне рамок

Linux-десктоп как целевая платформа; синхронизация между машинами; содержимое
коннекторов сверх живой проверки на чтение.

# Session pulse

Пульт сессий: одно место, где автор находит свои сессии Claude Code и Codex по всем
проектам, видит, о чём каждая и что после неё осталось, и открывает её заново.

## 1. Зачем

Сессия начинается в новом месте, работа не доделана, терминал закрывается — и сессию больше
не найти. Регистрация есть (`session-start`, `handoff`), но:

- **Запись появляется только при вызове скилла.** Хуки плагина на `SessionStart`
  (`inject-h2t-context`) и `SessionEnd` (`session-end-reap-codex`) записи не пишут. Сессия,
  где скилл не загрузили, следа не оставляет (#566).
- **В записи нет номера сессии и папки.** `session_id` — slug
  `<domain>-<project>-<topic>-<date>`, не UUID программы; `cwd` нет. Запись нельзя связать с
  разговором и открыть через `claude --resume <uuid>` (#566).
- **Исходные записи разговоров исчезают.** Claude Code хранил их около 30 дней; срок 365
  поставлен недавно, на диске записи только с 2026-09-26 (39 сессий верхнего уровня, 409
  файлов вместе с субагентами). Codex: 10 564 файла с 2026-03-22, большинство — вызовы
  конвейеров, а не разговоры.

Пример цены: разбор Telegram (ветка DOR `feat/tg-hygiene`, 21 незакоммиченный файл,
последняя работа 2026-09-04) автор помнил как брошенный, но найти сессию было негде.

Итог для автора — постоянный фон «много начато и брошено, не знаю где». Пульт его снимает.

## 2. Цели, не цели, анти-цели

**Цели**

1. Каждая живая сессия автора, Claude и Codex, попадает в записи сама — независимо от того,
   загружен ли скилл.
2. Пульт открывается по запросу и показывает сессии, сгруппированные по домену, проекту и
   репо, с короткой выжимкой «о чём» и статусом оставшейся работы.
3. Из пульта сессию можно открыть заново: готовая команда `--resume` с нужной папкой.
4. Фильтры: домен, проект, репо, итоговый статус работы, состояние PR, программа, даты.

**Не цели**

- Состояние репо без сессий (ветки конвейеров, старые stash). Его даёт `audit_map.py` и агент
  по запросу через git. В пульте — одна строка-ссылка на последний прогон `audit_map.py`
  (§5.6).
- Планирование. Высокоуровневый ход работ живёт в GitHub Projects у зарегистрированных
  проектов; пульт только ссылается на доску проекта.
- Сервер, синхронизация между машинами — как в спеке хранения (§13 там).

**Анти-цели** (провал, даже если «работает»)

- Шум: сессии субагентов, вызовы `codex exec` из конвейеров и из Claude, пустые сессии в
  списке. Из 358 сессий Claude в каталоге разбора 323 — субагенты.
- Вторая правда: пульт со своей базой, которая расходится с файлами-записями.
- Пульт, который надо держать открытым или который тормозит при открытии.

## 3. Ограничения, взятые из спеки хранения

Спека `2026-10-17-storage-and-governance.md` (#548) уже решила, где что лежит. Пульт её не
меняет, а дописывает:

- **Правда — файлы.** Записи сессий — `records/sessions/<машина>/<project-id>/<session_id>.md`
  с frontmatter (§5 там). «База как правда» там отклонена (§10). Пульт пишет только файлы.
- **Индекс `state/index.sqlite` — производный**, пересобирается, не синхронизируется. Таблицы
  `projects`, `repos`, `sessions` уже есть (`h2t_ops/lifecycle/index/schema.py`). Новое — новыми
  колонками и таблицами там же, с подъёмом `SCHEMA_VERSION` (несовпадение = пересборка).
- **Запись на диск — через `store.py`** (§7.2 там), класс `records`, одна машина на файл.
- **Связь сессия → проект → домен** — через `repos` (шаблон пути) и `projects` (онтология
  `repo-mapping.yaml`, `domains.yaml`). Папка вне онтологии → проект `unregistered`, сессия не
  теряется; по таким видно, что пора регистрировать.

## 4. Что решил автор (2026-10-19)

| Вопрос | Решение |

| Codex | Автор почти не работает в Codex напрямую, а вызывает его из Claude. Вызовы из Claude в пульт не попадают (как субагенты). Редкие прямые сессии Codex попадают только через ежедневный добор §5.2, с опозданием до суток; обёртки-запускателя нет. Приёмка «через минуту» — только для Claude |

## 5. Устройство

### 5.1. Запись сессии хуком (основа, #566)

Хуки h2t-core на `SessionStart` и `SessionEnd` пишут минимальную запись **всегда**:

- программа (`claude` / `codex`), UUID сессии программы, `cwd`, ветка git (если `cwd` в репо),
  время начала и конца, имя машины (`get_machine_name()`);
- проект и домен — по индексу (`repos`), иначе `unregistered`.

Ключ записи — UUID программы. `handoff` и `session-start` пишут в **ту же** запись (тот же
UUID), обогащая её `done` / `remains` / `artifacts`. Slug остаётся человеческим именем, но не
ключом. Сессии субагентов хук не регистрирует.

Если `SessionEnd` не пришёл (окно закрыли, процесс убит), временем конца считается время
последней строки записи разговора; его ставит добор §5.2. *(решение проектировщика)*

**Codex хуков не запускает** (`plugins/h2t-core/references/version-check.md:81`). Как его
сессии попадают в записи — §4, строка «Codex».

### 5.2. Добор по записям разговоров (страховка)

Раз в день сборщик проходит по `~/.claude/projects/**/*.jsonl` и `~/.codex/sessions/**/*.jsonl`
и создаёт записи для сессий, которые хук пропустил (хук упал, сессия до выпуска, другая
программа). Основа — `session_catalog.py` из разбора (`C:/dev/docs/standards/scripts/repo_audit/`):
он уже читает обе программы и даёт `tool, session_id, cwd, originator, start, end, user_msgs`.

Фильтр «живая сессия автора»:

- Claude: не субагент (файл не `agent-*`, записи не `isSidechain`), ≥1 сообщения автора.
- Codex: `originator` — интерактивный клиент, не `codex exec` из скрипта или из Claude.
  Точное значение поля для каждого случая — проба до плана (§7).
- Сессия, которую фильтр не смог отнести ни туда, ни сюда, записывается с пометкой
  `origin: unknown` и по умолчанию скрыта; флаг `--all` её показывает. Так шум не попадает в
  список, а живая сессия не теряется. *(решение проектировщика)*

### 5.3. Выжимка

Для сессии без `done` из `handoff` раз в день дешёвая модель пишет 1–3 строки «о чём сессия
и чем кончилась» по записи разговора и кладёт их во frontmatter записи с пометкой источника
(`summary_source: model`). Сессия с `handoff` берёт `done` (`summary_source: handoff`).
Повторно выжимка не делается, если запись разговора не менялась (по размеру и mtime).

### 5.4. Статус работы

При пересборке индекса — по ветке сессии, не по сессии: несколько сессий в одной ветке делят
статус и собираются под ней.

| Поле | Значения | Откуда |
|---|---|---|
| файлы | чисто / N незакоммиченных | `git status` в рабочей копии ветки |
| ветка | влита / не отправлена / отправлена без PR | git, сравнение по содержимому (squash, `.claude/rules/git.md`) |
| PR | нет / открыт / влит / закрыт | `gh pr list --head <ветка>` |
| задачи | открыта / закрыта по упомянутым `#N` | `gh issue view` |
| итог | **готово** / **ждёт PR** / **не отправлено** / **брошено с изменениями** | свод полей выше |

Данные GitHub сохраняются в индексе; пульт показывает, на какой момент.

*Решения проектировщика:*

- **«Ветка влита»** — если выполнено одно из двух: её PR в состоянии `MERGED`; или для каждого
  файла, который ветка меняет относительно точки ответвления, содержимое в ветке совпадает с
  содержимым в основной ветке. Второе правило ловит squash и rebase без PR. Ветка с
  коммитами после влитого PR считается не влитой.
- **«Упомянутые задачи»** — только из структурированных мест: `artifacts` записи `handoff`,
  номер в имени ветки (`fix/123-…`), `fixes|closes #N` в коммитах ветки и в описании её PR.
  Текст разговора не разбирается.

### 5.5. Два экрана над одним индексом

- **Терминал:** `h2t-ops sessions` (имя — на усмотрение плана) со списком и фильтрами
  (`--domain`, `--project`, `--repo`, `--status`, `--pr`, `--tool`, `--since`); строка сессии
  несёт команду открытия.
- **Браузер:** локальная статическая страница, собранная из индекса, с теми же фильтрами и
  группировкой домен → проект → репо → ветка → сессии. Только чтение.

### 5.6. Строка «работа без сессии»

Внизу обоих экранов: «Работа без сессии: N веток, M stash — подробнее», числа из последнего
прогона `audit_map.py`, ссылка на его отчёт.

`audit_map.py` сейчас пишет TSV только по указанному пути. Ежедневный добор §5.2 запускает его
сам и кладёт результат в постоянное место (`state/`, имя на усмотрение плана) с временем
прогона; пульт читает оттуда. *(решение проектировщика)*

## 7. Пробы до плана

1. **Хуки и UUID.** Отдаёт ли Claude Code UUID сессии и `cwd` в данных хука `SessionStart` /
   `SessionEnd`; срабатывает ли `SessionEnd` при закрытии окна терминала. Как то же получить в
   Codex.
2. **Codex: живая или машинная.** Значения `originator` (и других полей шапки) для
   интерактивной сессии, `codex exec` из скрипта, `codex exec` из Claude.
3. **Команда открытия.** Точный синтаксис возобновления для Claude (`claude --resume <uuid>`
   из исходной папки?) и для Codex; принимает ли каждая программа UUID вместе с папкой.
   Результат определяет поле «команда открытия» и тест приёмки.
**Результаты проб 1–3 (2026-10-19):**

- **Данные хука Claude.** Хуки пакета уже читают из входа события `session_id`, `cwd` и
  `transcript_path` (`h2t_ops/hooks/grade_guard.py:82-83,101`, `plain_guard.py:113-114`).
  Срабатывает ли `SessionEnd` при закрытии окна — не проверено; на этот случай есть правило
  конца по последней строке разговора (§5.1).
- **Codex: живая или машинная.** Поле `originator` по каталогу разбора (10 529 сессий):
  `codex_exec` 8374, `Claude Code` 1257, `codex-tui` 781, `Codex Desktop` 112,
  `codex_sdk_ts` 5. Живые — `codex-tui` и `Codex Desktop`; остальное машинное. Любое другое
  значение → `origin: unknown` (§5.2).
- **Команда открытия.** Codex: `codex resume <UUID> -C <папка>` (`codex resume --help`).
  Claude: `claude --resume <UUID>`, запуск из исходной папки — записи Claude лежат в каталоге,
  названном по папке проекта. Проверить на живой сессии при приёмке.
- **Попутно:** у `codex resume` есть флаг `--dangerously-bypass-hook-trust` («run enabled
  hooks»), то есть текущий Codex хуки поддерживает. Строка «Codex runs no hooks» в
  `version-check.md:81` может быть устаревшей. Для пульта это не важно (§4, строка «Codex»).

4. **Связь с h2t 4.0.** Не пересекается ли запись по UUID с миграцией `layout 1` (§8 спеки
   хранения): старые записи по slug должны остаться читаемыми.

## 8. Приёмка

- Сессия Claude, в которой не вызывали ни одного скилла, через минуту после старта видна в
  пульте с программой, папкой, проектом и командой открытия. Прямая сессия Codex — после
  ближайшего ежедневного добора.
- Команда открытия из пульта открывает именно ту сессию.
- Сессии субагентов и вызовы `codex exec` не видны ни в одном фильтре.
- Сессия, после которой в рабочей копии остались незакоммиченные файлы, видна со статусом
  «брошено с изменениями». (Пример из §1, `feat/tg-hygiene`, сюда не годится: записи
  разговоров до 2026-09-26 удалены. Если на неё нет записи `handoff`, её покажет только строка
  §5.6.)
- Фильтр по домену и по состоянию PR сужает список ровно до подходящих сессий.
- Пульт открывается без сети и без пересборки индекса.

# Storage and governance

Где пакет хранит данные, кто может туда писать и что за этим следит. У каждого класса данных
один каталог, у каждого провайдера один файл секрета. Путь знает один модуль, на диск пишет
тоже один модуль. Тесты держат ноль путей и записей мимо них.

Вторая из четырёх подсистем переработки (спека кода —
[2026-10-16-package-architecture.md](2026-10-16-package-architecture.md), её §11). Решение
владельца 2026-10-17: **4.0.0 не выпускается без этой подсистемы**. Код и данные переходят
одним выпуском. Связи: #548 (решение по корням), #541 (трекер).

## 1. Проблема — что измерено

Инвентарь 2026-10-17 на маке автора: код `h2t_ops/` на `main` 70214177 плюс листинг каталогов
по именам. Содержимое секретов не открывалось.

- **Секреты лежат в семи местах четырёх корней.** Порядок поиска в `core/secrets.py`:
  `H2T_SECRETS_FILE` → `~/.h2t/config/secrets/secrets.env` и остальные `*.env` по алфавиту
  → `~/.dor/secrets/secrets.env` → `~/.dor/secrets.env`. Токен Notion лежит в
  `~/.config/notion/token`. Google OAuth лежит в `~/.config/google-calendar-mcp/` (имя
  каталога осталось от первого MCP-сервера календаря, `core/google_auth.py:23`), его запасной
  путь — `~/.config/gmail/`. Есть ещё `~/.dor/google-credentials.json`. Telegram держит в
  `~/.config/telegram/` сессию вместе с курсорами и кэшами. Evals читают `~/.dor/secrets.env`
  мимо общей лестницы (`lifecycle/eval/session.py:28`), а `google_auth.py:64` делает
  `load_dotenv` при импорте.
- **Каждый корень синхронизируется по-своему.** `~/.h2t/config` — git-репо, `secrets/`
  защищены только `.gitignore`; в индексе 0 секретных файлов, на момент инвентаря 5 файлов
  изменены и не закоммичены. `~/.dor` — папка Syncthing, в ней 3 файла `*.sync-conflict-*`
  (secrets.env, registry.jsonl, manifest.jsonl) и `.stignore` с `/vault/.git`, потому что
  «побайтовая синхронизация ломает индекс». `~/.config` и остальной `~/.h2t` не
  синхронизируются никак.
- **Сессии лежат в двух каталогах.** В `~/.dor/sessions/` 235 md (машины `automata` и
  `macbook-pro-3`), в `~/.h2t/sessions/` 85 md (только `macbook-pro-3`). handoff пишет во
  второй (`lifecycle/handoff.py:58`), gather читает оба (`gather/sessions.py:40`). Последняя
  запись `automata` в общем каталоге датирована 2026-05-22. С этой стороны не проверено, но
  следует из кода: после этой даты сессии ноутбука не видны на маке.
- **Реестр сессий DOR остановился.** `~/.dor/registry.jsonl`: 4002 записи с 2026-03-17 по
  2026-05-22, 3995 из них с `AUTOMATA`, `status: started` у 3995.
- **У записывающих команд нет общего правила.** `research` пишет в `~/.h2t/research`;
  `meetgeek download` и `webhooks` — в зашитый `~/.dor/lake/…` (`meetgeek/recovery.py:121`,
  `commands.py:302`); курсор `granola sync` лежит в `~/.dor/lake/_cursors`; `telegram
  download-media` пишет в `~/Downloads`; `drive` и `gmail` требуют путь. Незнакомый
  пользователь получит `~/.dor/` от первого `meetgeek download`. Про vault пакет не знает:
  в коде ноль упоминаний. На диске два vault: `~/.dor/vault` (66 МБ) и `vault/` в чекауте DOR
  (3,2 МБ).
- **Онтологию разбирают три модуля, каждый по-своему.** `domains.yaml` (14 доменов) и
  `repo-mapping.yaml` (39 репо, cwd-шаблоны) разбирают `gather/project.py`,
  `detect_project.py` и `apply_registration.py`.
- **Пути и записи разбросаны.** В `h2t_ops/` (вместе с docstring и help):
  `Path.home()` — 45 строк в 31 файле, `expanduser(` — 28/14, `.dor` — 34/14,
  `.config/` — 16/5, `load_dotenv(` — 4/2, чтение `H2T_*_ROOT/SPOOL/FILE/DIR` — 15/13.
  Записи: `write_text/write_bytes` — 66/31, `open(…"w"/"a"/"x")` — 18/16,
  `os.replace/shutil.*` — 18/13, `unlink/remove/rmdir` — 15/9. Атомарная запись есть только
  в `setup/state.py`.
- **Есть внешние читатели.** POS API читает
  `~/.config/google-calendar-mcp/tokens.json` (`src/api/app/main.py:39`,

## 2. Требования

1. У каждого класса данных (§3) один каталог, у каждого провайдера один файл секрета.
2. Пакет ничего не синхронизирует. Каждый класс лежит в своём каталоге, и пользователь
   синхронизирует его чем хочет. Пакет записывает выбор и проверяет его через `doctor`.
3. Правда о каждой записи — файл с одним писателем. База данных бывает только производной
   (§5).
4. Путь знает только `core/paths.py`, на диск пишет только `core/store.py`, секреты читает
   только `core/secrets.py`. Тесты держат ноль обходов (§7).
5. В коде пакета ноль литералов `~/.dor`, `~/.config/<программа>`, имён программ в путях
   секретов.
6. Перенос — одна команда `h2t-setup sync`, копией со сверкой по хэшу, с откатом. Старые
   места весь 4.0.x остаются нетронутыми копиями и читаются как запасные.
7. Внешние читатели не ломаются в 4.0.x и получают контракт (§9).

## 3. Классы данных и раскладка

```text
~/.h2t/
├── config/            конфиг и онтология — правит пользователь (у автора это git-репо)
│   ├── domains.yaml, repo-mapping.yaml      онтология
│   ├── paths.yaml                           внешние места (§6) и выбор синхронизации
│   ├── telegram/chats.yaml                  выбор пользователя, не состояние
│   └── about-me/, personas/, rules/, …      личный контент
├── secrets/
│   ├── shared/        можно на нескольких машинах сразу — синхронизирует пользователь
│   └── local/         ломается или опасно при копировании — не синхронизируется
├── records/           только дописывать, у каждого файла один писатель, машина в пути
│   ├── sessions/<машина>/<project-id>/<имя-сессии>.md
│   ├── activity/<машина>.jsonl
│   └── evals/<машина>/<скилл>/<прогон>.json
├── data/              что пакет создал для пользователя или для других программ
│   ├── research/, creative/profiles/
│   └── telegram/mentions.json               публикуемый вывод, его читает POS (§9)
├── state/             машинное, пересобирается или терпит потерю
│   ├── machine.json, index.sqlite, evals-spool.sqlite
│   ├── cursors/<провайдер>.json, caches/<провайдер>/
│   └── run/                                 install.json, install.env, notified/, rollback/
├── logs/              hooks.jsonl, writes.jsonl, …
└── layout.json        версия раскладки
```

| Класс | Синхронизировать | Почему |
|---|---|---|
| `config/` | да (у автора git) | правится руками, изменения видны в diff |
| `secrets/shared/` | да | API-ключи, OAuth-клиенты и токены, которые провайдер разрешает держать на нескольких машинах |
| `secrets/local/` | **никогда** | сессия Telegram: один ключ авторизации с двух машин одновременно Telegram может отозвать (`AUTH_KEY_DUPLICATED`) |
| `records/` | да | у каждого файла один писатель, поэтому синхронизация файлами не путает |
| `data/` | по желанию | результаты |
| `state/`, `logs/` | **никогда** | живые базы, курсоры, локальная установка |

Различие между `records` и `data`. В `records` лежит то, что пакет записал о работе
пользователя, и в пути всегда есть машина. В `data` лежит то, что пакет создал для
пользователя или для другой программы. Всё, что читает внешняя программа, публикуется в
`data`, а не в `state`: состояние пакет вправе переложить, а публикуемый вывод нет.

## 4. Секреты: имена и правила

- **Файл называется по провайдеру**, как в `h2t-ops connectors`: `notion.env`,
  `telegram.env`, `meetgeek.env`, `exa.env`. Имена программ в путях запрещены.
- **Ключ внутри называется `<ПРОВАЙДЕР>_<ЧТО>`:** `NOTION_API_TOKEN`, `TELEGRAM_API_ID`.
- **Секрет, который не является строкой, хранится в формате провайдера:**
  `google.client.json`, `google.token.json`, `telegram.session`, `telegram.auth-state.json`.
- **По умолчанию секрет лежит в `shared`.** В `local` идёт только то, что провайдер запрещает
  держать на двух машинах сразу (сейчас это `telegram.session`), и состояние незавершённого
  входа (`telegram.auth-state.json`). Токен Google лежит в `shared`: Google разрешает
  несколько клиентов с одним refresh-токеном, и второй машине не нужен отдельный вход.
- **Файлы, которые пакету не принадлежат** (`getcourse.env`, `stripe.env` и т.п. из других
  репо), лежат в `secrets/shared/` под своими именами. Пакет их не читает и не проверяет на
  имя, только переносит.
- **Права.** На macOS и Linux — 0600 на файл и 0700 на каталог. На Windows эта защита
  слабее. Что делать там, определит проба §11.3, а спека честно пишет о результате.

## 5. Сессии и индекс

**Правда — md с frontmatter.** handoff пишет
`records/sessions/<машина>/<project-id>/<имя-сессии>.md`. Во frontmatter: `session_id`,
`machine`, `project`, `domain`, `date`, `branch`, `commits`, `done`, `remains`, `artifacts`.
Файл описывает себя сам. `latest.json` в каждом каталоге проекта (сейчас их 15) больше не
пишется: «последняя сессия проекта» — это запрос к индексу.

**Ключ — проект, а не путь.** Один репо лежит на маке и на Windows по разным путям. Через
`repo-mapping.yaml` оба пути сводятся к одному `project.id`, поэтому история проекта общая
для всех машин.

**Имя машины** задаётся один раз в `state/machine.json`: при миграции берётся уже
существующая подпапка (`macbook-pro-3`, `automata`), на новой машине — slug hostname.
Если файл пропал, появится новая подпапка. Читатель обходит все машины, поэтому ничего не
теряется.

**Индекс `state/index.sqlite`** — производная, никогда не синхронизируется.

- Таблицы: `projects` и `repos` строятся из онтологии, `sessions` — из frontmatter,
  `registry_history` — из разового импорта `~/.dor/registry.jsonl` (только чтение, файл
  остаётся DOR).
- Перед запросом gather досканирует изменения по mtime каталогов. Поэтому файлы, которые
  синхронизатор привёз с другой машины, видны при следующем `session-start`.
- В базе записан номер версии схемы. При несовпадении или повреждении база удаляется и
  собирается заново. Команды: `h2t-ops index rebuild`, `h2t-ops index query`.
- YAML онтологии разбирает только сборщик индекса. `gather`, `detect_project` и
  `apply_registration` спрашивают индекс. Пишет в YAML по-прежнему только
  `apply_registration` через `store.py`.

**`session-start`** показывает сессии **только текущего проекта**, но со всех машин:

```text
### Previous Session  (automata, 2 дня назад)
ветка feat/x, последний коммит a1b2c3d
⚠ на automata работали позже, чем здесь (macbook-pro-3, 5 дней назад) — git fetch
```

Предупреждение выводится только при расхождении.

**Сервер (VPS)** — вне рамок (§12). Раскладка его допускает: правда в файлах, поэтому сервер
становится ещё одним местом, куда реплицируются записи и откуда собирается индекс, а
`paths.yaml` может переадресовать класс `records` на смонтированный каталог. Пользователю
пакета сервер не нужен.

## 6. Внешние места и граница с POS

```yaml
# ~/.h2t/config/paths.yaml
version: 1
places:
  lake:  ~/.dor/lake       # сырьё: встречи, транскрипты, выгрузки
  vault: ~/.dor/vault      # знание; пишет только ингест (§6.2)
  kb:    ~/kb              # llm-kb-engine
  inbox: ~/Downloads       # одиночные файлы
vault_rules: ~/.h2t/config/rules/data-architecture.md
```

1. **У каждой записывающей команды есть место по умолчанию.** Встречи и транскрипты
   (Granola, MeetGeek) идут в `lake/<провайдер>/…`, вложения (Telegram, Drive, Gmail) — в
   `inbox`, research — в `data/research`. Явный `--dest` имеет приоритет. Если место не
   задано, пакет пишет в `~/.h2t/data/<место>/` и печатает, куда положил. `doctor`
   предлагает задать место.
2. **Граница с POS.** Коннекторы пишут только в `lake`. В `vault` пишет единственный
   инструмент — ингест (подсистема 4). Раскладку vault пакет не зашивает: правила берёт из
   файла POS, адрес которого лежит в `paths.yaml` (`vault_rules`). Поэтому пакету всё равно,
   какой из двух vault живой: он пишет в тот, на который указывает `paths.yaml`.
3. **Связь двусторонняя.** POS регистрирует свои места и правила в `paths.yaml`
   (`h2t-ops paths set lake <путь>`) и читает индекс и публикуемый вывод пакета.
4. **Переменные окружения** сводятся к одной форме `H2T_PATH_<МЕСТО>`
   (`H2T_PATH_LAKE`, `H2T_PATH_RECORDS`). Она перекрывает `paths.yaml`. Старые имена
   (`H2T_LAKE_ROOT`, `H2T_SESSION_ROOT`, `H2T_ACTIVITY_SPOOL`, `H2T_EVALS_ROOT`,
   `H2T_CONFIG_ROOT`, `H2T_SECRETS_FILE`, `H2T_KB_ROOT`) читаются как псевдонимы весь 4.0.x,
   `doctor` о них предупреждает.

## 7. Говернанс

### 7.1. Кто чем владеет

| Место | Владелец | Кто пишет |
|---|---|---|
| `~/.h2t/` целиком, кроме содержимого `config/` | пакет | только пакет и только через `store.py` |
| содержимое `config/` | пользователь | пользователь; пакет — только командой с согласия (`init-project`) и только в файлы известной схемы: `domains.yaml`, `repo-mapping.yaml`, `paths.yaml` |
| `lake`, `inbox` | тот, кто зарегистрировал (POS или пользователь) | пакет только добавляет, ничего не перезаписывает и не удаляет |
| `vault` | POS | только ингест |
| репо пользователя | пользователь | только `.claude/project-id` через `init-project` |

Вне этих мест пакет не пишет ничего, кроме явного `--dest`.

### 7.2. Три модуля доступа к диску

- **`core/paths.py`** — функция на каждый класс и место (`secrets_shared()`,
  `records_sessions(machine)`, `place("lake")`). Только он читает `paths.yaml`,
  `H2T_PATH_*` и старые псевдонимы, и только он знает старые места (для миграции и
  запасного чтения).
- **`core/secrets.py`** — единственный читатель секретов, из `secrets/{shared,local}`, а в
  4.0.x ещё из старых мест как запасных. Лестница из семи мест сводится к двум каталогам.
- **`core/store.py`** — единственный писатель. Каждый вызов называет класс или место
  (`records.sessions`, `place.lake`, `secrets.shared`), и модуль сверяет его с таблицей §7.1:
  - `lake`, `inbox` — только новый файл, существующий не перезаписывается;
  - `records` — только дописывание, путь обязан содержать машину;
  - `vault` — только с меткой вызывающего `ingest`;
  - `secrets` — права §4, значение никогда не попадает в лог;
  - `state` — свободная перезапись.

  Каждая запись атомарна: временный файл рядом и `os.replace`, как в `setup/state.py`.
  Каждая запись попадает в `logs/writes.jsonl`: место, путь, хэш, вызывающий; для секретов
  только имя ключа. Отсюда `doctor` и миграция знают, что создал пакет.

### 7.3. Тесты-ratchet

Числа замерены 2026-10-17 (§1). Тест знает их как потолок и падает при росте; цель — ноль.

| Обход вне модуля | Сейчас | Цель |
|---|---|---|
| `Path.home()`, `expanduser(`, `"~/"` вне `paths.py` | 45 + 28 + 3 | 0 (разбор пользовательского `--dest` идёт через `paths.expand_user_dest`) |
| `.dor`, `.config/` в коде | 34 + 16 | 0 |
| чтение `H2T_*` путей вне `paths.py` | 15 | 0 |
| `load_dotenv(` вне `secrets.py` | 4 | 0 |
| `write_text/write_bytes`, `open(…w/a/x)`, `os.replace`, `shutil.*`, `unlink/rmdir` вне `store.py` | 66 + 18 + 18 + 15 | 0 |
| литералы автора (тест подсистемы 1) | 7 | 0 |

Ещё два теста:
- **Имена секретов.** Каждый файл, который пакет пишет в `secrets/`, соответствует шаблону
  `<провайдер>.(env|client.json|token.json|session|auth-state.json)`, где провайдер есть в
  реестре коннекторов.
- **Таблица мест.** Каждое место из `paths.py` есть в таблице §3 или §6 этой спеки, и наоборот.
  Тест читает спеку.

Каждый тест считается только после того, как его видели красным на нарочно испорченном дереве
(правило репо).

### 7.4. `h2t-ops doctor` — проверка состояния

- **Ошибки:**
  - в индексе git-репо `config/` есть файл из `secrets/` или файл с ключом по шаблону
    (проверяется `git ls-files`, значения не печатаются);
  - `secrets/local` или `state/` лежит внутри синхронизируемой папки (выше по дереву
    `.stfolder`, `.dropbox` или `paths.yaml` объявляет их синхронизируемыми).
- **Предупреждения:**
  - данные найдены только в старом месте;
  - `*.sync-conflict-*` в `records/`, `secrets/`, `config/`;
  - неизвестный элемент в корне `~/.h2t` (у автора сейчас бэкап `.git` и манифесты
    2026-08-27);
  - устаревшая схема индекса;
  - старое имя переменной окружения;
  - место из `paths.yaml` не существует.

Отчёт печатает пути, имена ключей, хэши и длины — никогда значения.

### 7.5. Версия раскладки и миграции

`layout.json` хранит номер раскладки. Миграции нумеруются, каждая идемпотентна, их запускает
`h2t-setup sync` после установки CLI. Перед миграцией делается снимок в `state/run/rollback/`.

### 7.6. Как добавить место хранения

Правка `paths.py`, строка в таблице §3 или §6 этой спеки, тест. Без всех трёх изменение не
пройдёт тест таблицы мест.

## 8. Миграция `layout 1` и выпуск

**Выпуск.** 4.0.0 = код подсистемы 1 (уже на `main`) + эта подсистема. Номер остаётся 4.0.0.
Раздел «Известные ограничения → #548» в README и CHANGELOG заменяется описанием раскладки и
миграции.

**Шаги `layout 1`** (из `h2t-setup sync`, после установки CLI):

1. Снимок, проверка свободного места.
2. **Секреты.** Старые места (§1) читаются в нынешнем порядке лестницы. Каждый ключ
   кладётся в файл своего провайдера (по префиксу ключа и таблице провайдеров в коде). Если у
   ключа в двух местах разные значения, побеждает то, которое код читает сегодня; второе
   `doctor` показывает по хэшу. Ключи неизвестного провайдера идут в
   `secrets/shared/other.env`, и `doctor` их перечисляет. JSON-файлы Google и сессия Telegram
   копируются под новыми именами.
3. **Сессии этой машины** из `~/.h2t/sessions/<машина>/` и `~/.dor/sessions/<машина>/`
   переносятся в `records/sessions/<машина>/`, с frontmatter из `latest.json` и из тела md.
   Сессии других машин сюда не копируются: они придут через синхронизацию `records/` с той
   машины, которая их писала. Иначе две машины создали бы одинаковые файлы независимо.
4. Telegram делится на три части (§3, §4); evals переезжают в `records/evals/<машина>/` и
   `state/evals-spool.sqlite`; activity — в `records/activity/<машина>.jsonl`; курсоры — в
   `state/cursors/`.
5. Импорт `registry.jsonl` в индекс, сборка индекса.
6. Сверка каждой копии по хэшу, `MOVED-TO.txt` в каждом старом каталоге, `layout.json = 1`.

Если файл с тем же именем уже есть по новому адресу, при одинаковом хэше это тот же файл, а
при разном сохраняются оба (`<имя>.from-<источник>`), и `doctor` их показывает.

**Порядок у автора, две машины:**
1. Мак: `h2t-setup sync`, затем в Syncthing — папки `~/.h2t/secrets/shared` и
   `~/.h2t/records`.
2. Ноутбук: то же самое. Его сессии с мая приезжают на мак.
3. Обе машины: `doctor` и `session-start` в одном репо.

До шага 2 ноутбук работает на старых запасных местах.

**Новый пользователь.** Старых мест нет, раскладка создаётся сразу, `~/.dor` не появляется,
места не заданы, `doctor` предлагает задать `lake` и `inbox`.

**Окно совместимости.** Весь 4.0.x старые места остаются нетронутыми копиями и читаются как
запасные, `doctor` предупреждает. В 4.1 запасное чтение удаляется; старые файлы пакет не
удаляет никогда, это делает пользователь после предупреждения `doctor`.

**Откат.** Миграция копирует, поэтому откат — удалить новое и вернуть прежний `layout.json`.
Команда `h2t-setup sync --rollback-layout`.

## 9. Внешние читатели

| Читатель | Что читает | В 4.0.x | Контракт |
|---|---|---|---|
| POS API (calendar, gmail, main, docker-compose, plist) | `~/.config/google-calendar-mcp/tokens.json` | старый файл остаётся копией; пакет обновляет оба файла, пока старый существует | `h2t-ops paths get secret:google.token` |
| POS API (telegram_service) | `~/.config/telegram/mentions_cache.json` | пакет пишет оба файла, пока старый существует | `data/telegram/mentions.json`, `h2t-ops paths get data:telegram.mentions` |
| rejuve, `POS/CLAUDE.md` | `~/.h2t/config/secrets/*.env` | старые файлы остаются копиями | `h2t-ops paths get secret:<провайдер>` |

Двойная запись в 4.0.x идёт через `store.py` с меткой `compat` и удаляется в 4.1. До выпуска
в POS и rejuve заводятся issues с этой таблицей. Репо чужое, правка — их сторона.

## 10. Решения

| Вопрос | Решение | Отклонено |
|---|---|---|
| Корни | **один корень `~/.h2t` + `paths.yaml` для внешнего** (#548, вариант A) | несколько корней с записью |
| Синхронизация | **пакет не синхронизирует**, классы разведены по каталогам | пакет настраивает Syncthing |
| Секреты на машинах | **`shared` + `local`** | всё синхронно (ломает Telegram); всё локально |
| Перенос | **`h2t-setup` переносит сам: копия, хэш, метка, запасное чтение один выпуск** | команды для ручного переноса; вечная лестница |
| База данных | **индекс, производный от файлов**; сервер позже, отдельно | база как правда (две машины = конфликт синхронизации) |
| vault | **пишет только ингест, правила от POS** | коннекторы пишут в vault |
| Ингест | **отдельная подсистема**; здесь только контракт | ингест в этой спеке |
| Запись | **один модуль `store.py`** | правила владения на дисциплине |
| `registry.jsonl` | **разовый импорт в индекс, только чтение** | не трогать |

## 11. Пробы до плана

1. **Syncthing.** Даёт ли `sync-conflict` одинаковый файл, независимо созданный на двух
   машинах. От ответа зависит, можно ли обеим машинам мигрировать `secrets/shared`
   независимо.
2. **Индекс.** Время полной сборки на 320 md с frontmatter и инкрементального прохода
   (бюджет `session-start` — 3 с вместе с gather).
3. **Права на Windows.** Что дают 0600/ACL для `secrets/` под Git Bash и Python; какую защиту
   можно честно обещать.
4. **Google refresh-токен на двух машинах.** Подтвердить, что один токен в `shared` работает
   с обеих машин и не отзывается.

## 12. Приёмка

- На каждой из двух машин после миграции `session-start` в одном репо показывает последнюю
  сессию **этого проекта** с любой машины, с именем машины. Сессии других проектов в брифинг
  не попадают. Если последняя сессия была на другой машине, брифинг это говорит.
- `doctor` чистый.
- Каждый коннектор проходит свой `doctor`, ключи сверены по хэшу.
- **Контроль:** старые каталоги переименованы — коннекторы работают. Это доказывает, что код
  читает новые места.
- Ratchet-тесты §7.3 на нуле.
- Новый пользователь в пустом HOME: после `sync` нет `~/.dor` и `~/.config/<программа>`.

## 13. Вне рамок и бэклог

1. **Скилл синхронизации.** Режим, который помогает настроить Syncthing или git для классов
   §3 и проверяет результат.
2. **Сервер (VPS) для автора.** Реплика `records` и индекс на сервере, включается по
   желанию. Отдельная спека.
3. **Ингест POS** (lake → vault по правилам POS) — подсистема 4.
4. **Связка ключей ОС** (Keychain, Credential Manager) для `secrets/local`.
5. **Модель онтологии** (домены, проекты) не меняется; меняются только её читатели.

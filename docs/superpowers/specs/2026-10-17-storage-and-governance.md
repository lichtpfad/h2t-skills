# Storage and governance

Где пакет хранит данные, кто может туда писать и что за этим следит. У каждого класса данных
один каталог, у каждого провайдера один файл секрета. Путь знает один модуль, на диск пишет
тоже один модуль. Тесты держат ноль путей и записей мимо них.

Вторая из четырёх подсистем переработки (спека кода —
[2026-10-16-package-architecture.md](2026-10-16-package-architecture.md), её §11). Решение
владельца 2026-10-17: **4.0.0 не выпускается без этой подсистемы**. Код и данные переходят
одним выпуском. Связи: #548 (решение по корням), #541 (трекер).

Версия 6: правки после трёх раундов ревью (два Codex + дискриминатор, затем Codex по диффу
дважды; журнал в §14), результаты проб на маке (§11), поправки по коду при написании плана
(§14, «v5») и ответы владельца на вопросы плана 2026-10-18 (§14, «v6»): две переменные путей
вместо семейства, access-токен Google не хранится, vault — общая с POS переменная, имя машины
без файла, миграция — отдельная команда `h2t-setup layout`; по пробам ноутбука (§11) токен
Google у каждой машины свой в `local`.

## 2. Требования

1. У каждого класса данных (§3) один каталог, у каждого провайдера один файл секрета.
2. Пакет ничего не синхронизирует. Каждый класс лежит в своём каталоге, и пользователь
   синхронизирует его чем хочет. Пакет записывает выбор и проверяет его через `doctor`.
3. Правда о каждой записи — файл, в который пишет одна машина. База данных бывает только
   производной (§5).
4. Путь знает только `core/paths.py`, на диск пишет только `core/store.py`, секреты читает
   только `core/secrets.py`. Тесты держат ноль обходов (§7.3) и проверяют это запуском (§7.3,
   тест песочницы).
5. В коде пакета ноль литералов `~/.dor`, `~/.config/<программа>`, имён программ в путях
   секретов.
6. Перенос — одна команда `h2t-setup sync`, копией с проверкой, журналом и откатом. Старые
   места весь 4.0.x остаются нетронутыми копиями и читаются как запасные.
7. Внешние читатели не ломаются в 4.0.x и получают контракт (§9).
8. Контракт установки из спеки 4.0 (`~/.h2t/run/install.json`, `install.env`, §6.4 там) не
   меняется.

## 3. Классы данных и раскладка

```text
~/.h2t/
├── run/               бутстрап установки — место зафиксировано спекой 4.0 (§6.4 там), его
│                      читает bash (hooks/run:58); install.json, install.env, notified/, rollback/
├── config/            конфиг и онтология — правит пользователь (у автора это git-репо)
│   ├── domains.yaml, repo-mapping.yaml      онтология
│   ├── paths.yaml                           внешние места (§6) и выбор синхронизации
│   └── about-me/, personas/, rules/, …      личный контент
├── secrets/
│   ├── shared/        можно на нескольких машинах сразу — синхронизирует пользователь
│   └── local/         ломается или опасно при копировании — не синхронизируется
├── records/           записи о работе; в каждый файл пишет одна машина, машина в пути
│   ├── sessions/<машина>/<project-id>/<session_id>.md
│   ├── activity/<машина>.jsonl
│   ├── evals/<машина>/<скилл>/<прогон>.json
│   └── imports/dor-registry.jsonl          разовая копия ~/.dor/registry.jsonl, только чтение
├── data/              что пакет создал для пользователя или для других программ
│   └── research/, creative/profiles/
├── state/             машинное, пересобирается или терпит потерю
│   ├── index.sqlite, evals-spool.sqlite
│   ├── cursors/<провайдер>.json
│   ├── backups/<файл>.<YYYYmmdd-HHMMSS>    копии config/*.yaml перед правкой пакетом
│   └── telegram/dialogs_bootstrapped
├── logs/              hooks.jsonl, writes.jsonl, …
└── layout.json        версия раскладки
```

| Класс | Синхронизировать | Почему |
|---|---|---|
| `run/` | **никогда** | установка этой машины |
| `config/` | да (у автора git) | правится руками, изменения видны в diff |
| `secrets/shared/` | да | API-ключи, OAuth-клиенты и refresh-токены, которые провайдер разрешает держать на нескольких машинах |
| `secrets/local/` | **никогда** | сессия Telegram: один ключ авторизации с двух машин одновременно Telegram может отозвать (`AUTH_KEY_DUPLICATED`) |
| `records/` | да | в каждый файл пишет одна машина, поэтому синхронизация файлами не путает |
| `data/` | по желанию | результаты |
| `state/`, `logs/` | **никогда** | живые базы, курсоры, кэши, журналы |

**Одна машина на файл.** В `records/` путь содержит машину, поэтому две машины никогда не
пишут один файл. Несколько процессов одной машины (параллельные сессии) пишут в общий файл
только через операцию `append` с межпроцессной блокировкой (§7.2).

Различие между `records` и `data`. В `records` лежит то, что пакет записал о работе
пользователя. В `data` — то, что пакет создал для пользователя или для другой программы. Всё,
что читает внешняя программа, публикуется в `data`, а не в `state`: состояние пакет вправе
переложить, а публикуемый вывод нет.

**Машиночитаемая таблица мест.** Её сверяет тест §7.3 с тем, что экспортирует `paths.py`.
Новое место без строки здесь тест не пропустит.

```yaml places
- {id: run,             kind: fixed, class: run,     sync: never}
- {id: config,          kind: class, class: config,  sync: user}
- {id: secrets.shared,  kind: class, class: secrets, sync: user}
- {id: secrets.local,   kind: class, class: secrets, sync: never}
- {id: records.sessions, kind: class, class: records, sync: user}
- {id: records.activity, kind: class, class: records, sync: user}
- {id: records.evals,   kind: class, class: records, sync: user}
- {id: records.imports, kind: class, class: records, sync: user}
- {id: data,            kind: class, class: data,    sync: user}
- {id: state,           kind: class, class: state,   sync: never}
- {id: logs,            kind: class, class: logs,    sync: never}
- {id: lake,            kind: place, class: external, sync: owner}
- {id: inbox,           kind: place, class: external, sync: owner}
- {id: vault,           kind: place, class: external, sync: owner}
- {id: kb,              kind: place, class: external, sync: owner}
- {id: repo,            kind: place, class: external, sync: owner}
- {id: harness,         kind: place, class: external, sync: owner}
- {id: tmp,             kind: place, class: external, sync: never}
- {id: layout,          kind: file,  class: root,    sync: never}
```

`harness` — каталог Claude Code (`CLAUDE_CONFIG_DIR` или `~/.claude`), `tmp` — временный
каталог системы (`tempfile.gettempdir()`). `layout` — один файл `layout.json` в корне
`~/.h2t`, вне классов; он переезжает вместе с `H2T_PATH_ROOT`, в отличие от `run/`.
`vault` — место из переменной `H2T_PATH_VAULT` (по умолчанию `~/.dor/vault`), а не из
`paths.yaml` (§6 п. 5).

## 4. Секреты: имена и правила

- **Файл называется по провайдеру.** Провайдер — это внешний сервис, а не коннектор:
  у коннектора `research` два провайдера, `exa` и `jina`. Реестр «коннектор → провайдеры»
  лежит в коде рядом с реестром коннекторов. Примеры: `notion.env`, `telegram.env`,
  `meetgeek.env`, `exa.env`, `jina.env`. Имена программ в путях запрещены.
- **Ключ внутри называется `<ПРОВАЙДЕР>_<ЧТО>`:** `NOTION_API_TOKEN`, `TELEGRAM_API_ID`.
- **Секрет, который не является строкой, хранится в формате провайдера:**
  `google.client.json`, `google.token.json`, `telegram.session`, `telegram.auth-state.json`.
- **По умолчанию секрет лежит в `shared`.** В `local` идёт то, что провайдер запрещает
  держать на двух машинах сразу (`telegram.session`), состояние незавершённого входа
  (`telegram.auth-state.json`) и вход в Google этой машины (`google.token.json`, ниже).
- **Google.** В `shared/google.client.json` лежит OAuth-клиент — один на все машины. В
  **`local/google.token.json`** — refresh-токен и выданные scopes **этой машины** (решение
  владельца 2026-10-18 по пробе §11.4: у мака и ноутбука разные входы, `sha256[:12]`
  refresh-токенов `ffadbd08aa1f` и `4ac3fa1e3925`). Каждая машина входит сама, файлы токена
  не синхронизируются, поэтому нет ни «главной копии», ни правила «чья новее»: писатель у
  файла один — пакет этой машины (POS только читает, §1). **Access-токен нигде не хранится**
  (решение владельца 2026-10-18): каждый процесс `h2t-ops` получает его по refresh-токену в
  памяти, когда тот нужен, и выбрасывает. Цена — один запрос к Google на команду. Сегодня
  пакет переписывает весь файл при каждом обновлении access-токена (лениво, при первой
  команде после истечения, §1). Теперь файл токена пишется только при входе
  (`h2t-ops google auth`) и когда Google выдал **новый** refresh-токен.
- **Файлы, которые пакету не принадлежат** (`getcourse.env`, `stripe.env` и т.п. из других
  репо), лежат в `secrets/shared/` под своими именами. Пакет их не читает, не проверяет на
  имя и только переносит.
- **Служебные файлы миграции:** `other.env` (ключи неизвестного провайдера) и
  `<имя>.from-<источник>` (проигравшее значение при конфликте, §8). Тест имён знает их как
  явные исключения.
- **Права.** На macOS и Linux — 0600 на файл и 0700 на каталог. На Windows `os.chmod(0o600)`
  ничего не меняет (режим читается как `0o666`), а файл наследует ACL профиля: владелец,
  Administratoren, SYSTEM (проба §11.3, 2026-10-17). Пакет на Windows права не ставит и не
  проверяет: тесты прав, проверка `doctor` и сверка миграции работают только на POSIX и на
  Windows молчат. Защита там — ACL профиля пользователя.

## 5. Сессии и индекс

**Правда — md с frontmatter.** handoff пишет
`records/sessions/<машина>/<project-id>/<session_id>.md` операцией `replace` (§7.2):
повторный handoff той же сессии обновляет её запись, а новая сессия получает новый файл.
Во frontmatter: `session_id`, `machine`, `project`, `domain`, `date`, `branch`, `commits`,
`done`, `remains`, `artifacts`, а у перенесённых ещё `migrated_from: <путь>@<sha256>`.
Файл описывает себя сам. `latest.json` в каждом каталоге проекта (сейчас их 15) больше не
пишется: «последняя сессия проекта» — это запрос к индексу.

**Ключ — проект, а не путь.** Один репо лежит на маке и на Windows по разным путям. Через
`repo-mapping.yaml` оба пути сводятся к одному `project.id`, поэтому история проекта общая
для всех машин.

**Имя машины** берётся по правилу, которое уже есть в коде, `get_machine_name()`
(`gather/sessions.py:148-159`: `H2T_MACHINE_NAME` → `DOR_MACHINE_NAME` → hostname). Файла с
именем нет: `h2t-setup` закрепляет `H2T_MACHINE_NAME` в `env` настроек Claude Code
(`setup/legacy.py:383` `ensure_machine_name`, ADR 0003), потому что hostname на macOS плывёт
(#491; на маке автора `LocalHostName` за месяц сменился с `MacBook-Pro-3` на `MacBook-Pro-4`,
проверено 2026-10-18). Все читатели имени — gather, handoff, activity — работают внутри Claude
Code и видят эту переменную. Существующая подпапка в старых каталогах не выбирает имя, а
только подтверждает его. На маке автора в синхронизируемом `~/.dor/sessions` лежат обе
подпапки, `automata` и `macbook-pro-3`, поэтому выбор по подпапке был бы неоднозначен. Если
подпапки с вычисленным именем нет, а старые сессии есть, миграция останавливается и просит
назвать машину (`h2t-setup layout migrate --machine <имя>`); названное имя закрепляется тем же
`ensure_machine_name`.

**Индекс `state/index.sqlite`** — производная, никогда не синхронизируется.

- Таблицы: `projects` и `repos` строятся из онтологии, `sessions` — из frontmatter,
  `registry_history` — из `records/imports/dor-registry.jsonl`. Копия лежит в `records`,
  поэтому пересборка индекса историю не теряет.
- Перед запросом gather проверяет `stat` (mtime и размер) каждого листового каталога сессий и
  каждого файла онтологии и досканирует изменившееся. Файлы `*.sync-conflict-*` считаются
  изменением. Поэтому файлы, которые синхронизатор привёз с другой машины, и правка YAML на
  месте видны при следующем `session-start`.
- В базе записан номер версии схемы. При несовпадении или повреждении база удаляется и
  собирается заново. Команды: `h2t-ops index rebuild`, `h2t-ops index query`.
- YAML онтологии разбирает только сборщик индекса. `gather`, `detect_project` и
  `apply_registration` спрашивают индекс. Пишет в YAML по-прежнему только
  `apply_registration`, через `store.py`.

**`session-start`** показывает сессии **только текущего проекта**, но со всех машин:

```text
### Previous Session  (automata, 2 дня назад)
ветка feat/x, последний коммит a1b2c3d
⚠ на automata работали позже, чем здесь (macbook-pro-3, 5 дней назад) — git fetch
```

Предупреждение выводится только при расхождении.

**Сервер (VPS)** — вне рамок (§13). Раскладка его допускает: правда в файлах, поэтому сервер
становится ещё одним местом, куда реплицируются записи и откуда собирается индекс (переадресация
класса `records` на смонтированный каталог — дело той спеки: в 4.0 переменных на класс нет,
§6 п. 5). Пользователю
пакета сервер не нужен.

## 6. Внешние места и граница с POS

```yaml
# ~/.h2t/config/paths.yaml
version: 1
places:
  lake:  ~/.dor/lake       # сырьё: встречи, транскрипты, выгрузки
  kb:    ~/kb              # llm-kb-engine
  inbox: ~/Downloads       # одиночные файлы
vault_rules: ~/.h2t/config/rules/data-architecture.md
```

Vault в `paths.yaml` не задаётся: его адрес — общий договор пакета и POS, переменная
`H2T_PATH_VAULT` (п. 5).

1. **У каждой записывающей команды есть место по умолчанию.** Встречи и транскрипты
   (Granola, MeetGeek) идут в `lake/<провайдер>/…`, вложения (Telegram, Drive, Gmail) — в
   `inbox`, research — в `data/research`. Явный `--dest` имеет приоритет, но тоже проходит
   проверку пути (§7.2). Если место не задано, пакет пишет в `~/.h2t/data/<место>/` и
   печатает, куда положил. `doctor` предлагает задать место.
2. **Граница с POS.** Коннекторы пишут только в `lake`. В `vault` пишет единственный
   инструмент — ингест (подсистема 4). Раскладку vault пакет не зашивает: правила берёт из
   файла POS, адрес которого лежит в `paths.yaml` (`vault_rules`). Пишет пакет в тот vault, на
   который указывает `H2T_PATH_VAULT`; тот же адрес читает POS.
3. **Связь двусторонняя.** POS регистрирует свои места и правила в `paths.yaml`
   (`h2t-ops paths set lake <путь>`) и читает индекс и публикуемый вывод пакета. Vault пакет
   и POS берут из одной переменной `H2T_PATH_VAULT`; сегодня POS держит `~/.dor/vault`
   зашитым (§1), поэтому в POS заводится issue (§9).
4. **Места не пересекаются.** `paths.py` при чтении `paths.yaml` разрешает каждое место через
   `realpath` и отклоняет файл, если одно место лежит внутри другого (например `inbox` внутри
   `vault`) или внутри `~/.h2t`. Vault участвует в проверке со своим адресом из переменной.
5. **Переменных путей две** (решение владельца 2026-10-18):
   - `H2T_PATH_ROOT` переносит весь `~/.h2t`, кроме `run/` (его место зафиксировано
     спекой 4.0); ею же тесты изолируют раскладку;
   - `H2T_PATH_VAULT` — адрес vault, общий для пакета и POS; по умолчанию `~/.dor/vault`.
     Задавать её нужно, только если vault переезжает, и тогда в двух местах: в окружении
     shell и в plist POS API (launchd окружение shell не наследует).

   Переменных на класс или место нет: внешние места задаются в `paths.yaml`. Старые имена
   (`H2T_LAKE_ROOT`, `H2T_SESSION_ROOT`, `H2T_ACTIVITY_SPOOL`, `H2T_EVALS_ROOT`,
   `H2T_EVALS_SPOOL`, `H2T_CONFIG_ROOT`, `H2T_SECRETS_FILE`) пакет 4.0 **не читает**. Миграция
   переносит значение внешнего места в `paths.yaml` (`H2T_LAKE_ROOT` → `lake`), файл
   `H2T_SECRETS_FILE` читает один раз как ещё один источник секретов (§8 п. 2), а об
   остальных пишет «удалить переменную». `doctor` предупреждает о каждой заданной. Две
   переменные не наши и не места хранения: `H2T_KB_ROOT` читает `llm-kb-engine` (в коде
   пакета 0 чтений), `H2T_DEV_ROOT` говорит, где лежит код соседних репо, а не данные.

**Протокол манифеста коннектора.** Прерванная запись не должна оставлять файл, который
коннектор потом не признаёт своим.

1. Коннектор готовит содержимое и считает хэши будущих файлов.
2. Дописывает в манифест строку `pending`: пути, ожидаемые хэши и для каждого пути — был ли
   он уже своим (есть в прошлой строке `committed`).
3. Пишет файлы: новый путь — операцией `create`, свой путь — операцией `replace`. Если на
   новом пути уже лежит файл, который не значится своим, `create` отклоняет запись, файл
   остаётся нетронутым, а `doctor` его показывает.
4. Дописывает строку `committed` с итоговыми хэшами.
5. Только после этого сдвигает курсор.

**Строка `pending` сама по себе права на файл не даёт.** При восстановлении коннектор
признаёт своим только файл, чей хэш совпал с ожидаемым в `pending`, то есть файл, который
опубликовала именно эта операция. Файл с другим хэшем не трогается. План проверяет прерывание
между каждой парой шагов, а также чужой файл на пути до записи и во время восстановления.

Вне этих мест пакет не пишет ничего, кроме явного `--dest`.

### 7.2. Три модуля доступа к диску

- **`core/paths.py`** — функция на каждое место из таблицы §3 (`secrets_shared()`,
  `records("sessions", machine)`, `place("lake")`, `vault()`, `run_dir()` — фиксированный
  `~/.h2t/run`). Только он читает `paths.yaml`, `H2T_PATH_ROOT` и `H2T_PATH_VAULT`, только он
  знает старые места (для миграции и запасного чтения) и старые имена переменных (чтобы
  миграция и `doctor` о них сказали). `paths.expand_user_dest()` разбирает пользовательский
  `--dest`.
- **`core/secrets.py`** — единственный читатель секретов, из `secrets/{shared,local}`, а в
  4.0.x ещё из старых мест как запасных. `research` и evals переходят на него.
- **`core/store.py`** — единственный писатель. Четыре операции, у каждого класса своя:

  | Операция | Как | Где |
  |---|---|---|
  | `create` | `O_CREAT\|O_EXCL`: временный файл, затем атомарное переименование без перезаписи; существующий файл — ошибка | новые файлы в `lake`, `inbox`; новые md сессий |
  | `append` | `O_APPEND`, одна запись `write()` под межпроцессной блокировкой (`fcntl.flock`, на Windows `msvcrt.locking`) | `records/activity`, манифесты коннекторов |
  | `replace` | временный файл рядом и `os.replace` | `state`, `config`, `secrets`, md текущей сессии, свои файлы коннектора в `lake` |
  | `managed` | `store.py` разрешает и проверяет путь, выставляет права, журналирует открытие, а писать в файл отдаёт библиотеке | `index.sqlite`, `evals-spool.sqlite`, `telegram.session` |

  **Проверка по физическому пути.** Каждую запись `store.py` классифицирует по `realpath`
  назначения против разрешённых корней всех мест — независимо от того, какое место назвал
  вызывающий и откуда пришёл путь (`--dest`, симлинк). Запись внутрь `vault` отклоняется,
  если она идёт не через `store.ingest_write`; тест держит у этой функции ровно одно место
  импорта — модуль ингеста. Секреты пишутся с правами §4, значение никогда не попадает в лог.

  **Испорченный `paths.yaml` не останавливает запись внутри `~/.h2t`.** Если файл не
  разбирается или места пересекаются, `store.py` по-прежнему классифицирует места пакета и
  пишет в них (handoff, activity, логи хуков, сам `h2t-ops paths set`, который файл чинит).
  Отклоняются только записи за пределами `~/.h2t`, где без `paths.yaml` нельзя сказать, чьё
  это место; отказ называет ошибку файла (правило `gates.md`: проверка не встаёт между
  сделанной работой и её сохранением).

  Каждая запись попадает в `logs/writes.jsonl`: место, путь, хэш, вызывающий; для секретов
  только имя ключа. Это журнал для `doctor` и для человека, корректность на нём не держится:
  принадлежность файлов в `lake` определяет манифест коннектора, откат миграции — журнал
  миграции (§7.5). Хранение: ротация при 10 МБ, пять файлов.

### 7.3. Тесты

**Текстовые ratchet-тесты — частичные.** Они ловят известные написания, но не доказывают, что
обхода нет. Числа замерены 2026-10-17 (§1). Тест знает их как потолок и падает при росте; цель
— ноль.

| Обход вне модуля | Сейчас | Цель |
|---|---|---|
| `Path.home()`, `expanduser(`, `"~/"`, `os.environ["HOME"]`, `USERPROFILE` вне `paths.py` | 45 + 28 + 3 + … | 0 |
| `.dor`, `.config/` в коде | 34 + 16 | 0 |
| чтение `H2T_*` путей вне `paths.py`; `H2T_DEV_ROOT` не считается — это адрес кода соседних репо, а не место хранения | 15 | 0 |
| `load_dotenv(`, `read_text/read_bytes/open(` на путях секретов вне `secrets.py` | 4 + … | 0 |
| `write_text/write_bytes`, `open(…w/a/x)`, `os.replace`, `shutil.*`, `unlink/rmdir`, `sqlite3.connect`, `tempfile.`, `logging.FileHandler`, `json.dump(` в дескриптор вне `store.py` | 66 + 18 + 18 + 15 + … | 0 |
| литералы автора (тест подсистемы 1) | 7 | 0 |

Числа с «…» план замеряет первой задачей и вписывает в тест.

**Тест песочницы — то, что доказывает.** Каждый коннектор и каждая команда, которая пишет на
диск, запускается под временным HOME. В нём разрешены для записи только объявленные места, а
каталоги старых мест присутствуют, но закрыты на запись. Запись вне объявленного или чтение
секрета из старого места при наличии нового — красный тест.

- **Исключения для совместимости узкие.** Запись в старое место разрешена только для зеркала
  токена Google (§9) через операцию с меткой `compat` и только для `MOVED-TO.txt` во время
  миграции. Отдельные тесты: разрешённая запись `compat`
  проходит, любая другая запись в старое место красная.
- **Чтение старого секрета при новом.** Для файлов, у которых есть один новый двойник
  (`tokens.json` ↔ `google.token.json`, `credentials.json` ↔ `google.client.json`,
  `auth_state.json` и `session.session` Telegram, `~/.config/notion/token` ↔ `notion.env`),
  чтение старого файла при существующем новом — красный тест, кто бы ни читал, `secrets.py`
  тоже. Общие env-файлы лестницы держат несколько провайдеров сразу, поэтому для них правило
  «провайдер с новым файлом не читается из старого» проверяет модульный тест `secrets.py`, а не
  аудит.
- **Кто трогал файл.** Тест ставит `sys.addaudithook` на события `open`, `os.rename`,
  `os.remove`, `os.rmdir`, `os.mkdir`, `shutil.*`, `sqlite3.connect` и `subprocess.Popen`.
  Для каждого события с путём под `secrets/` или в объявленных местах он проверяет стек
  вызова: в нём должен быть `secrets.py` или `store.py`. Для `managed` это делегирование,
  которое `store.py` зарегистрировал на конкретный путь и библиотеку до открытия.
  Отрицательные тесты красные: прямое чтение `secrets/shared/exa.env` из коннектора, прямая
  запись, переименование и удаление внутри разрешённого `lake`, открытие базы без
  делегирования.
- **Чего этот тест не видит, сказано прямо.** Расширения на C, которые сами делают системные
  вызовы, и дочерние процессы после `Popen` аудит не наблюдает. Здесь гарантия — это
  песочница с правами на каталоги, а не стек вызова. Поэтому вывод теста — «обходов через
  Python не найдено», а не «обходов ноль».

**Тест имён секретов.** Каждый файл, который пакет пишет в `secrets/`, соответствует шаблону
`<провайдер>.(env|client.json|token.json|session|auth-state.json)`, где провайдер есть в
реестре «коннектор → провайдеры». Явные исключения: `other.env`, `*.from-*`, файлы, которые
пакет не создавал (чужие `.env`).

**Тест таблицы мест.** Блок `yaml places` из §3 сравнивается с местами, которые экспортирует
`paths.py`, в обе стороны.

**Тест полного круга бутстрапа.** `hooks/run` запускается против `install.env`, который
записал `state.py` через `paths.run_dir()`, а не против файла, созданного тестом по
зашитому пути.

**Тест блокировки.** Взаимное исключение проверяется детерминированно: процесс A берёт
блокировку и держит её, процесс B пытается дописать и обязан ждать, пока A её не отпустит
(проверка по отметкам времени и по порядку строк). Мутация «убрать блокировку» делает этот
тест красным. Отдельно — нагрузка: два процесса по 1000 записей дают 2000 целых строк.

Каждый тест считается только после того, как его видели красным на нарочно испорченном дереве
(правило репо).

### 7.4. `h2t-ops doctor` — проверка состояния

- **Ошибки:**
  - в git-репо `config/` отслеживается файл из `secrets/`, или в отслеживаемом файле есть
    ключ из реестра провайдеров с непустым значением (`git ls-files`, затем `git show :путь`
    по каждому файлу; печатаются путь и имя ключа, не значение);
  - `secrets/local`, `state/`, `logs/` или `run/rollback/` лежит внутри синхронизируемой
    папки. Симлинки сначала разрешаются. Признаки: выше по дереву `.stfolder` или `.dropbox`,
    либо `paths.yaml` объявляет каталог синхронизируемым.
- **Предупреждения:**
  - данные найдены только в старом месте;
  - `*.sync-conflict-*` в `records/`, `secrets/`, `config/`;
  - неизвестный элемент в корне `~/.h2t` (у автора сейчас бэкап `.git` и манифесты
    2026-08-27);
  - устаревшая схема индекса;
  - задана старая переменная окружения: пакет её больше не читает (§6 п. 5); подсказка —
    куда перенесено значение или что переменную пора удалить;
  - место из `paths.yaml` или vault из `H2T_PATH_VAULT` не существует;
  - `*.bak*` в `config/` — копии 3.x, их место теперь `state/backups/`;
  - в 4.1: в старом каталоге сессий есть машина, у которой нет каталога в `records/`.
- Проверку синхронизации `doctor` сообщает как **подтверждено**, **объявлено** или
  **неизвестно**, а не одним «чисто»: признаки синхронизатора могут быть не видны.

Отчёт печатает пути, имена ключей, хэши и длины — никогда значения.

### 7.5. Версия раскладки, миграции, откат

- `layout.json` хранит номер раскладки. Миграции нумеруются, каждая идемпотентна. Их
  выполняет команда `h2t-setup layout migrate [--machine <имя>]`; `h2t-setup sync` вызывает
  её после установки CLI. Команда `layout` работает в том исполнителе, который её запустил,
  включая установку editable из чекаута: так миграцию можно прогнать и принять до выпуска
  4.0.0, а `sync` на editable-установке по-прежнему отказывает.
- **Журнал миграции** `run/rollback/<id>/journal.jsonl`: по строке на каждый файл, который
  миграция создала, — путь, источник, хэш на момент создания. Каждая фаза отмечает
  завершение, поэтому прерванная миграция продолжается с места, а не начинается заново.
  Журнал не ротируется. Каталог отката создаётся с правами 0700, файлы секретов в нём 0600;
  он удаляется через 30 дней после успешной миграции.
- **Откат** `h2t-setup layout rollback --sync-paused`: удаляет только файлы из журнала, чей
  текущий хэш совпадает с записанным, возвращает прежнее содержимое файлов, которые миграция
  дополнила (оно сохранено в каталоге отката), и возвращает прежний `layout.json`. Изменённые после миграции
  файлы и файлы из каталогов других машин он не трогает, а перечисляет. Перед откатом команда
  требует поставить синхронизацию `records/` и `secrets/shared/` на паузу: иначе удаление
  уйдёт на другие машины.

### 7.6. Как добавить место хранения

Правка `paths.py`, строка в блоке `yaml places` §3 (и в таблице §7.1, если это внешнее место),
тест. Без всех трёх изменение не пройдёт тест таблицы мест.

## 8. Миграция `layout 1` и выпуск

**Выпуск.** 4.0.0 = код подсистемы 1 (уже на `main`) + эта подсистема. Номер остаётся 4.0.0.
Раздел «Известные ограничения → #548» в README и CHANGELOG заменяется описанием раскладки и
миграции.

**Шаги `layout 1`** (команда `h2t-setup layout migrate`; `h2t-setup sync` вызывает её после
установки CLI; каждая фаза пишет журнал §7.5):

1. Снимок, проверка свободного места, имя машины (§5).
2. **Секреты.** Миграция обходит **все** старые места явно. `H2T_SECRETS_FILE` пакет 4.0 не
   читает (§6 п. 5), но миграция, если переменная задана, читает её файл один раз как ещё
   один источник. Куда что идёт:

   | Источник | Что | Куда | Чьё значение главное при конфликте |
   |---|---|---|---|
   | `*.env` во всех старых местах | ключ с префиксом провайдера | `shared/<провайдер>.env` | порядок нынешней общей лестницы |
   | `~/.dor/secrets.env` | `H2T_EVALS_*` | `shared/h2t-evals.env` | значение из `~/.dor/secrets.env`: только его читают evals сегодня |
   | `*.env` | ключ без известного провайдера | `shared/other.env` | порядок лестницы |
   | `~/.config/notion/token` | токен | `shared/notion.env` → `NOTION_API_TOKEN` | env-файл, если ключ есть и там |
   | `~/.config/google-calendar-mcp/`, `~/.config/gmail/`, `~/.dor/google-credentials.json` | клиент Google | `shared/google.client.json` | `google-calendar-mcp` — его читает код сегодня |
   | `~/.config/google-calendar-mcp/tokens.json`, `~/.config/gmail/token.json` этой машины | токен Google | `local/google.token.json` (права 0600), у каждой машины свой | `google-calendar-mcp`; конфликта между машинами нет — каждая переносит свой |
   | `~/.config/telegram/config.json` | `api_id`, `api_hash` | `shared/telegram.env` → `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` | — |
   | `~/.config/telegram/session.session`, `auth_state.json` | сессия, вход | `local/telegram.session`, `local/telegram.auth-state.json` (права 0600) | — |
   | `~/.config/telegram/dialogs_bootstrapped` | отметка | `state/telegram/dialogs_bootstrapped` | — |
   | чужие `.env` (getcourse, stripe, …) | файл целиком | `shared/<то же имя>` | — |

   **Полный порядок старшинства** для ключей общей лестницы, от старшего к младшему:
   уже существующий файл по новому адресу (повторный запуск или правка пользователя после
   прошлой миграции) → файл `H2T_SECRETS_FILE`, если переменная задана (сегодня при ней код
   читает только его) → `~/.h2t/config/secrets/secrets.env` → остальные
   `~/.h2t/config/secrets/*.env` по алфавиту → `~/.dor/secrets/secrets.env` →
   `~/.dor/secrets.env` → `~/.config/notion/token`. Для `H2T_EVALS_*` старше всех
   `~/.dor/secrets.env`, как в таблице.

   Проигравшее значение сохраняется в `<файл>.from-<источник>` рядом и показывается `doctor`
   по хэшу.
3. **Сессии этой машины** из `~/.h2t/sessions/<машина>/` и `~/.dor/sessions/<машина>/`
   переносятся в `records/sessions/<машина>/` с frontmatter: из `latest.json` и заголовка md.
   Сессии других машин сюда не копируются: они придут через синхронизацию `records/` с той
   машины, которая их писала. Иначе две машины создали бы одинаковые файлы независимо.
4. Telegram делится на три части (§3, §4); `mentions_cache.json`, `chats.yaml`,
   `last_sync.json` не переносятся (§1); evals переезжают в `records/evals/<машина>/` и
   `state/evals-spool.sqlite`; activity — в `records/activity/<машина>.jsonl` **без строк,
   которые оставили тесты** (#441): строки с `session_id` или `project` из фикстур набора
   тестов не переносятся, у автора это 1279 строк из 1445 (замерено 2026-10-18); курсоры — в
   `state/cursors/`; `~/.dor/registry.jsonl` копируется в `records/imports/dor-registry.jsonl`;
   копии `config/*.yaml.bak*` уходят в `state/backups/` и из `config/` удаляются (откат их
   возвращает); `paths.yaml` создаётся, если его нет: `lake` из `H2T_LAKE_ROOT` или
   существующего `~/.dor/lake`, `inbox` — `~/Downloads`, если он есть.
5. Сборка индекса.
6. **Проверка.** Байтовые копии (JSON Google, сессия Telegram, evals, registry) сверяются по
   хэшу. activity — по правилу: копия равна источнику без отфильтрованных строк, число
   отфильтрованных — в отчёте. Преобразованные — по правилу. Для секретов **до любой записи** снимается
   базовое множество пар `(ключ, sha256(значение))`: старые источники с ключами,
   переведёнными в новые имена по таблице п. 2 (`api_id` → `TELEGRAM_API_ID`), плюс пары уже
   существующих новых файлов и копий `*.from-*`. После миграции объединение пар новых файлов
   и копий `*.from-*` должно совпасть с этим множеством: ни одно значение не потеряно.
   Отдельно проверяется, что в каждом новом файле стоит значение, старшее по порядку п. 2:
   победители вычисляются **до записи** и записываются в журнал парами
   `(файл, ключ, sha256)`, сверка идёт против журнала, а не против повторного расчёта по уже
   записанным файлам. Базовое множество тоже берётся из журнала, в том числе при продолжении
   прерванной миграции.
   Тест: повторный запуск после того, как пользователь поменял ключ в новом файле, а в
   старых источниках этого значения нет; для сессий тело после frontmatter
   побайтно равно исходному файлу, а хэш источника записан в `migrated_from`. Затем
   `MOVED-TO.txt` в каждом старом каталоге и `layout.json = 1`.

Если файл с тем же именем уже есть по новому адресу, при одинаковом хэше это тот же файл, а
при разном сохраняются оба (`<имя>.from-<источник>`), и `doctor` их показывает.

**Несколько машин.** Первой мигрирует одна машина, затем пользователь включает синхронизацию
`~/.h2t/secrets/shared` и `~/.h2t/records`. Каждая следующая машина мигрирует после того, как
`secrets/shared` к ней приехал: тогда существующий новый файл старше всех, и конфликта
синхронизации нет (§11.1). До своей миграции машина работает на старых запасных местах.
Выкатка на машинах автора — в `docs/superpowers/plans/2026-10-18-storage-rollout.md`.

**Новый пользователь.** Старых мест нет, раскладка создаётся сразу, `~/.dor` не появляется,
места не заданы, `doctor` предлагает задать `lake` и `inbox`.

**Окно совместимости.** Весь 4.0.x старые места остаются нетронутыми копиями и читаются как
запасные, `doctor` предупреждает. В 4.1 запасное чтение удаляется; старые файлы пакет не
удаляет никогда, это делает пользователь после предупреждения `doctor`.

## 10. Решения

| Вопрос | Решение | Отклонено |
|---|---|---|
| Корни | **один корень `~/.h2t` + `paths.yaml` для внешнего** (#548, вариант A) | несколько корней с записью |
| Синхронизация | **пакет не синхронизирует**, классы разведены по каталогам | пакет настраивает Syncthing |
| Секреты на машинах | **`shared` + `local`** | всё синхронно (ломает Telegram); всё локально |
| Перенос | **`h2t-setup` переносит сам: копия, проверка, журнал, запасное чтение один выпуск** | команды для ручного переноса; вечная лестница |
| База данных | **индекс, производный от файлов**; сервер позже, отдельно | база как правда (две машины = конфликт синхронизации) |
| vault | **пишет только ингест, правила от POS, проверка по физическому пути** | коннекторы пишут в vault |
| Ингест | **отдельная подсистема**; здесь только контракт | ингест в этой спеке |
| Запись | **один модуль `store.py`, четыре операции** | правила владения на дисциплине; одна операция «атомарная замена» |
| `run/` | **остаётся `~/.h2t/run`** (контракт спеки 4.0) | перенос в `state/run` |
| `registry.jsonl` | **копия в `records/imports`, индекс читает её** | импорт только в индекс |
| Токен Google | **у каждой машины свой, в `local`; клиент общий в `shared`; зеркало в старое место в одну сторону** (владелец, 2026-10-18, по пробе §11.4) | главная копия в `shared` с правилом «чья новее» (входы машин разные); двусторонняя запись |
| Access-токен Google | **не хранится; каждый процесс получает его в памяти** (владелец, 2026-10-18) | кэш в `state`; полное зеркало при каждом обновлении (запасной вариант, если POS не обновляет токен сам) |
| Переменные путей | **две: `H2T_PATH_ROOT` и `H2T_PATH_VAULT`**; внешние места — в `paths.yaml`; старые имена не читаются (владелец, 2026-10-18) | семейство `H2T_PATH_<место>` плюс псевдонимы 3.x: два набора дают вопрос «кто главнее» |
| Адрес vault | **переменная `H2T_PATH_VAULT`, общая с POS** | строка в `paths.yaml`: POS её не читает |
| Имя машины | **`H2T_MACHINE_NAME` в настройках Claude (ADR 0003)** | файл `state/machine.json`: второй источник без читателя вне Claude; аппаратный UUID: нечитаемое имя каталога |
| Запуск миграции | **команда `h2t-setup layout migrate/rollback`, `sync` её вызывает** | флаги на `sync`: на editable-установке `sync` отказывает, и миграцию нельзя принять до выпуска |

## 11. Пробы до плана

Пробы проведены 2026-10-17 на macOS и Windows. Здесь вопросы и выводы для устройства пакета;
замеры по машинам — в документе выкатки `docs/superpowers/plans/2026-10-18-storage-rollout.md`.

1. **Syncthing.** Даёт ли `sync-conflict` одинаковый файл, независимо созданный на двух
   машинах. От ответа зависит, могут ли машины мигрировать `secrets/shared` независимо.
   **Не проведена:** на Windows-машине пробы Syncthing не стоял. Пока ответа нет, действует
   безопасный порядок §8: следующая машина мигрирует после того, как `secrets/shared` к ней
   приехал.
2. ~~**Индекс.**~~ Полная сборка SQLite по 318 md — 15–66 мс, проход `stat` по каталогам и
   файлам онтологии — меньше 1 мс (тёплый кэш, macOS). Правка YAML на месте меняет mtime и
   размер файла, но **не** mtime каталога. Отсюда §5: смотреть `stat` каждого файла
   онтологии. Холодный кэш и Windows не замерены.
3. ~~**Права на Windows.**~~ `os.chmod(f, 0o600)` без эффекта, режим читается как `0o666`; ACL
   файла наследуется от профиля: владелец, администраторы, SYSTEM. Вывод в §4: на Windows
   пакет права не ставит и не проверяет, защита — ACL профиля.
4. ~~**Google на нескольких машинах.**~~ `sha256[:12]` refresh-токенов на двух машинах разные,
   то есть каждая машина входила отдельно. Решение владельца: токен у каждой машины свой, в
   `local/google.token.json`; клиент общий в `shared` (§4).
5. ~~**Блокировка на Windows.**~~ `msvcrt.locking` между процессами работает: второй процесс
   ждал, пока первый держал блокировку. Устройство `append` §7.2 остаётся.
6. **POS с протухшим access-токеном** (к решению §4). POS API с `GOOGLE_TOKEN_FILE` на файле,
   где `expiry` в прошлом: отвечает ли одна команда календаря без 401. Делается до выпуска
   (документ выкатки, Step 3).

## 12. Приёмка

- На каждой машине после миграции `session-start` в одном репо показывает последнюю
  сессию **этого проекта** с любой машины, с именем машины. Сессии других проектов в брифинг
  не попадают. Если последняя сессия была на другой машине, брифинг это говорит.
- `doctor` чистый, проверка синхронизации — «подтверждено» или «объявлено».
- Каждый коннектор проходит свой `doctor`, ключи сверены по хэшу.
- **Контроль:** старые каталоги переименованы — коннекторы работают. Это доказывает, что код
  читает новые места.
- Тест песочницы, тест полного круга бутстрапа и ratchet-тесты §7.3 зелёные, ratchet на нуле.
- Откат на тестовой машине удаляет только файлы из журнала; сессия, записанная после
  миграции, остаётся.
- Новый пользователь в пустом HOME: после `sync` нет `~/.dor` и `~/.config/<программа>`.
- POS отвечает на команду календаря с протухшим access-токеном в `tokens.json` (§11.6);
  иначе включается запасной вариант зеркала (§9).

## 13. Вне рамок и бэклог

1. **Скилл синхронизации.** Режим, который помогает настроить Syncthing или git для классов
   §3 и проверяет результат.
2. **Сервер (VPS) для автора.** Реплика `records` и индекс на сервере, включается по
   желанию. Отдельная спека.
3. **Ингест POS** (lake → vault по правилам POS) — подсистема 4.
4. **Связка ключей ОС** (Keychain, Credential Manager) для `secrets/local`.
5. **Модель онтологии** (домены, проекты) не меняется; меняются только её читатели.

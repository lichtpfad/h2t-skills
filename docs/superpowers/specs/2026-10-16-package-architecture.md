# Package architecture

Весь исполняемый код — в одном пакете со своим Python и закреплёнными зависимостями.
Плагины несут тексты, ресурсы-данные и обёртку хуков. Выпуск — один тег, на который
закреплены оба канала. Совместимость каналов — номер протокола, а не номер версии.

Версия 2: переписана после adversarial-ревью Codex (раунд 1, 18 находок, журнал в §13).

Первая из четырёх подсистем переработки (§11). Связи: #541 (трекер установки),
[спека wizard'а](2026-10-14-setup-wizard.md).

## 1. Проблема — что измерено

Цель — пак готов к работе у незнакомого человека без помощи автора: репозиторий
публичный. Сейчас им с трудом пользуется и сам автор. Инвентарь 2026-10-16 (субагент,
только чтение, `file:line`; четыре пункта перепроверены основной сессией):

- **Код в двух-трёх копиях.** Общая библиотека: `lib/`, ручная копия
  `plugins/h2t-core/lib/` (совпадение держит только `test_vendored_lib_parity.py`) и
  замороженная при сборке `h2t_ops/_plugin_payload/`. Коннекторы drive, meetgeek, research
  написаны дважды: `h2t_ops/connectors/drive/client.py` (1677 строк) «mirrors»
  `skills/drive/scripts/drive_cli.py` (531), всего ~5100 строк на обе версии. Поиск файла
  секретов реализован заново в 6–7 местах. Установка и диагностика — в трёх местах:
  `setup_h2t.py` (836 строк), `h2t-ops doctor` (всегда exit 0), скилл; плюс устаревший
  `setup.sh`.
- **Два канала исполнения одного кода.** Девять точек входа CLI — загрузчики скриптов
  плагина через лестницу из пяти путей (`plugin_entrypoints.py:1-22`). Из 26 `SKILL.md`
  12 падают без CLI, 8 запускают свои `scripts/*.py`, 7 не делают ни того ни другого.
  В кэше h2t-core 3.2.61 — 55 файлов `.py`, которым Claude Code не даёт ни Python, ни
  зависимостей: отсюда резолвер интерпретатора, заглушка Store, `uv run` за 0,9 с (D9),
  `jq` (D1).
- **Личное автора в поставке.** ID базы задач Notion в коде коннектора
  (`notion/commands.py:65`) и в daily brief; `Asia/Jerusalem` в пяти местах; регулярка
  `Projects/DOR|Projects/newsengine` (`detect_project.py:35`); имена машин в шаблонах.
- **Версии ничего не говорят.** Пакет всегда `0.2.1` (D6), у пяти плагинов свои пять
  номеров. Старый `h2t-hook --version` не печатает версию, а ищет обработчик с именем
  `--version` и выходит с кодом 5 (проверено 2026-10-16).

## 2. Цель и критерии успеха

Каждый критерий — тест или измерение с порогом.

1. **Одна реализация.** Общая библиотека, каждый коннектор, поиск секретов, doctor —
   по одному месту. Ratchet по картам исполняемых файлов (§8, E0) не растёт и в конце
   равен нулю для `plugins/`.
2. **Детерминированная установка.** Один тег → одно и то же окружение на любой машине:
   тот же Python (минорная версия), те же версии всех зависимостей. Тест: две установки
   тега в разные пустые каталоги дают одинаковый `uv pip freeze`.
3. **Бюджеты по событиям** (тёплый запуск, p95, по 20 прогонов, macOS и Windows):

   | Событие | Бюджет | Python |
   |---|---|---|
   | `UserPromptSubmit`, обычное сообщение | 50 мс | не запускается |
   | `UserPromptSubmit`, слэш-команда session-скилла | 3 с | да, gather |
   | `Stop` (оба хука вместе) | 300 мс macOS / 600 мс Windows — уточняется пробой §10 | да |
   | `PostToolUse` | 150 мс | только если хуку есть что делать |
   | `SessionStart` | 1 с | один раз |

4. **Ожидаемый вывод, а не тишина.** Для каждого хука и события записан ожидаемый вывод:
   gather обязан вернуть брифинг, guard без нарушения — пустой ответ. Тест сверяет
   вывод, а не только отсутствие ошибки.
5. **Обе комбинации версий работают функционально:** новый плагин + старый CLI и старый
   плагин + новый CLI — session-start даёт брифинг, handoff пишет запись, ошибок нет.
6. **Обновление восстанавливаемо.** Сбой на любом шаге `update` (сеть, сборка, конфликт)
   оставляет рабочую предыдущую установку. Тест вводит сбой после каждого шага.
7. **Литералы автора не прибавляются.** Ratchet по известным значениям не растёт; до нуля
   их доводит подсистема 2, у которой есть куда их переложить (§11).

## 3. Принятые решения

| Вопрос | Решение | Отвергнуто |
|---|---|---|
| Где код | **A**: весь Python в пакете; плагины — тексты, данные-ресурсы, обёртка хуков | B как общий подход: `uv run` 0,9 с на Stop-хук на Windows (D9). Допустим для отдельного редкого инструмента с минимальными зависимостями — только по замеру. C как конечное состояние: два канала и путаница версий остаются |
| Как переезжать | **Сначала добавить, потом удалить** (expand/contract, §8). Новый путь работает параллельно со старым минимум один выпуск, удаление — после | удалить и перенести в одном шаге: промежуточный выпуск сломан (ревью, №1) |
| Совместимость каналов | **Номер протокола** `h2t-hook --protocol` + явная обработка старого CLI | сравнение номеров версий: «≥ N» пропускает несовместимое, «= N» ругается на совместимое (ревью, №4) |
| Выпуск | **Один тег на оба канала**: CLI из тега, marketplace `owner/repo#<тег>` (проба 2026-10-16: работает, кэш встаёт на коммит тега; SHA не принимается) | CLI из тега, плагины с main |
| Зависимости | **Закреплены**: Python 3.12, constraints из `uv.lock` на тег | диапазоны из `pyproject.toml`: разные окружения на разных машинах (ревью, №8) |
| Имя дистрибутива | **Остаётся `h2t-ops`**; граница в `CLAUDE.md` меняется: `h2t-ops` — весь пак | переименование в `h2t-skills`: замена требует сначала снести рабочую установку — обе ставят команды с одинаковыми именами (ревью, №2) |
| Интерфейс | команды на PATH с `--json` | MCP-сервер: отдельная установка и конфиг в каждом харнессе |

## 4. Поддерживаемые среды

Без этой таблицы «работает у незнакомца» непроверяемо.

| Харнесс | ОС | Оболочка хуков | Хуки | Скиллы и CLI |
|---|---|---|---|---|
| Claude Code | macOS | bash | да | да |
| Claude Code | Windows | Git Bash | да | да |
| Claude Code | Windows | без Git Bash | не поддерживается: `bash hooks/run` не стартует. `env` wizard'а проверяет Git Bash до установки плагинов | да |
| Codex | macOS, Windows | — | **не рассчитываем**: хуки требуют trust review конкретного определения, поддержка по версиям не проверена (D10) | да |
| Linux | — | — | не проверяется отдельно (вне рамок wizard'а) | — |

Следствие для Codex: всё, что в Claude Code делает хук (gather, проверка совместимости),
в Codex делает сам скилл первой командой (`h2t-gather`, `h2t-ops doctor --quick`).
Скилл не полагается на хук ни в одном харнессе — хук только ускоряет.

## 5. Что где лежит

```text
h2t_ops/                       пакет — единственное место исполняемого кода
  core/         пути, секреты, конфиг, чтение JSON, ошибки, конверт ответа
  lifecycle/    gather, handoff, activity, eval          (из lib/)
  hooks/        по модулю на хук
  connectors/   по одной реализации на коннектор
  setup/        wizard
  tools/        docs-lint, drawio, сборщик creative      (из scripts/ плагинов)
  resources/    данные инструментов: шаблоны creative (base, profiles, shared),
                defaults drawio, known_secrets — читаются через importlib.resources
  cli.py        точки входа

plugins/<name>/                плагин
  skills/<skill>/SKILL.md, references/*.md
  hooks/hooks.json             "command": "bash \"${CLAUDE_PLUGIN_ROOT}/hooks/run\" <hook>"
  hooks/run                    обёртка, протокол — §6
  hooks/legacy/                только на время перехода (§8), затем удаляется
```

Ресурсы, которые инструмент ищет рядом с собой (`assembler.py:12` —
`Path(__file__).parent / "base"`; drawio — `config/defaults.yaml`), переезжают в
`h2t_ops/resources/` вместе с кодом. Проверка — установка wheel вне репозитория и вне
кэша плагинов (§9).

Зависимости: базовые и extras; OCR (`rapidocr-onnxruntime`, ~250 МБ из 404 МБ
окружения) — в `h2t-ops[ocr]`.

## 6. Контракт вызовов

### Обёртка `hooks/run`

Её задача — не дать плагину сломать сессию при любом состоянии CLI. Поэтому она шире
«однострочного вызова»:

1. **Найти CLI.** По порядку: `uv-receipt.toml` установки h2t-ops (точный `install-path`
   команды `h2t-hook` — uv его записывает), затем PATH. Каталог `~/.local/bin` не
   угадывается: его меняют `UV_TOOL_BIN_DIR` и XDG.
2. **Проверить протокол.** `h2t-hook --protocol` печатает `h2t-hook-protocol 1`. Старый
   CLI отвечает `Plugin entrypoint script not found: hooks-handlers/--version`-подобным
   текстом и кодом 5 — это распознаётся как «устаревший CLI». Результат кэшируется в
   `~/.h2t/run/protocol` по пути и mtime найденного исполняемого файла, чтобы не
   запускать Python на каждом событии.
3. **Выбрать путь.**

   | Состояние | Что делает |
   |---|---|
   | CLI с нужным протоколом | `h2t-hook <name>` |
   | CLI устарел или отсутствует, идёт переход (§8) | обработчик из `hooks/legacy/` — поведение как сегодня |
   | CLI устарел или отсутствует, переход закончен | только на `SessionStart`: одна строка с точной командой (ниже); на остальных событиях — exit 0 без вывода |

   Сообщение только на `SessionStart` — это «один раз за сессию» без общего состояния
   между процессами: событие и так приходит один раз.
4. **Формат сообщения по событию** — JSON с `hookSpecificOutput.additionalContext` для
   событий, где его читает модель, `systemMessage` для остальных. Обёртка пишет его сама,
   готовым литералом: Python-эмиттер на этом пути недоступен.
5. **Дешёвый предфильтр** для `UserPromptSubmit`: решение «есть ли слэш-команда
   session-скилла» принимается на bash (так уже работает `gather-on-prompt` после #543).

Текст сообщения при отсутствии CLI содержит команду, которая работает без CLI:

```text
h2t: CLI не установлен. Установить: uvx --from "<источник тега>" h2t-setup
```

Если нет и `uv` — строка установки `uv` для платформы.

### Обработчик `h2t-hook <name>`

- читает stdin байтами и декодирует явно (`errors="replace"`) — урок `400 invalid high
  surrogate`;
- выбирает канал по событию одним эмиттером для всех путей выхода;
- при исключении — одна строка `h2t hook <name> failed: <класс> → h2t-ops doctor`,
  подробности в `~/.h2t/logs/hooks.jsonl`;
- ненулевой код — только при намеренной блокировке действия.

Модуль хука — чистая функция `handle(event: dict) -> Reply`.

### Скиллы

`SKILL.md` вызывает только команды CLI, всегда с `--json`. Конверт и коды выхода
коннекторов (0 ok, 1 provider, 2 usage, 3 config, 4 auth, 5 not found, 6 network)
распространяются на все команды. В каждой ошибке — `hint` с точной следующей командой.
`compatibility` каждого скилла называет нужный протокол CLI и внешние зависимости.

## 7. Выпуск, установка, обновление

### Выпуск

Тег `v<ver>` на коммите, где одновременно:
- `pyproject.toml`, все `plugin.json` и `marketplace.json` несут `<ver>`;
- `constraints.txt` экспортирован из `uv.lock` (`uv export`) и закоммичен;
- один `CHANGELOG.md`.

Между мержем и тегом пользователей нет: README и wizard ставят только из тега.

### Установка

```bash
uv tool install --python 3.12 -c "<constraints.txt на теге>" "h2t-ops @ <источник тега>"
claude plugin marketplace add "lichtpfad/h2t-skills#v<ver>" --json
```

Источник тега — архив GitHub (`…/archive/refs/tags/v<ver>.zip`), если проба §10
подтвердит, что uv ставит из него без git; иначе `git+…@v<ver>` и Git в списке
предпосылок (`env` проверяет). Бутстрап, когда CLI ещё нет, — `uvx --from` с тем же
источником.

### Обновление — `h2t-setup update`

1. Показывает «было → станет» и изменения из CHANGELOG. Ждёт «да».
2. **Пробная установка** нового тега в отдельный временный `UV_TOOL_DIR` /
   `UV_TOOL_BIN_DIR`: разрешение зависимостей и сборка. Сбой — стоп, рабочая установка
   не тронута.
3. Установка поверх: спецификация берётся из `uv-receipt.toml` (extras, `--with`), меняется
   только ref. Extras не теряются.
4. Marketplace и плагины в каждом харнессе — отдельными командами: обновление
   marketplace и обновление плагина в Claude Code — разные операции.
5. Проверка: `h2t-hook --protocol`, `verify`. Сбой — откат на предыдущий тег той же
   командой из receipt.
6. Сообщает, что открытые сессии работают на старой версии до `/reload-plugins` или
   новой сессии. Кэш плагинов не чистит: файлы могут принадлежать ещё открытой сессии.

Работает и через протокол `next`/`answer` wizard'а.

### Чекаут разработчика

`update` чекаут не трогает: показывает коммит, ветку, грязное ли дерево и состояние
окружения. Отдельная команда `h2t-setup dev-sync` переустанавливает editable-окружение
(`uv tool install --reinstall --editable <путь>`) — ставит новые зависимости, Git не
трогает.

## 8. Миграция — сначала добавить, потом удалить

**Инвариант каждого выпуска:** обе комбинации (новый плагин + старый CLI, старый плагин +
новый CLI) функционально работают — критерий 2.5, тест в CI.

| # | Шаг | Почему комбинации живы |
|---|---|---|
| E0 | **Карта и сторожа.** Таблица каждого исполняемого файла пака (`.py`, bash-обработчики, `setup.sh`): потребители, куда переезжает, срок жизни обёртки. Ratchet по этой карте. Фиксация текущего порядка поиска секретов и fixtures с конфликтом (одинаковый ключ с разными значениями в двух местах) | ничего не меняется |
| E1 | **Пакет получает собственные реализации** `core/`, `lifecycle/`, `hooks/`, `resources/`, `--protocol`. Точки входа CLI перестают загружать скрипты плагина и зовут пакет. Порядок поиска секретов — ровно прежний, теперь в одном модуле | новый CLI больше не зависит от файлов плагина — работает со старым плагином. Старый плагин запускает свои обработчики, как раньше |
| E2 | **Плагины получают `hooks/run`**, текущие обработчики переезжают в `hooks/legacy/` без изменений | новый плагин + старый CLI → `legacy/`; + новый CLI → `h2t-hook` |
| E3 | **Скиллы переходят на команды CLI**; скрипты коннекторов и инструментов остаются тонкими обёртками, зовущими CLI | старые вызовы работают через обёртки |
| E4 | **Выпуск 4.0.0 по §7**: одна версия, constraints, тег, `h2t-setup update`, установка из тега | — |
| C1 | **Удаление**, не раньше чем через один выпуск после E4: `hooks/legacy/`, `lib/`, `plugins/h2t-core/lib/`, `_plugin_payload`, лестница путей, `resolve-h2t-python.sh`, скрипты-обёртки, `setup.sh`, корневой `hooks/hooks.json`. Ratchet → 0 | после C1 старый CLI получает сообщение на `SessionStart` с командой обновления |

Ни один шаг не меняет данных в `~/.h2t`, `~/.dor`, `~/.config`. Приоритет источников
секретов E1 сохраняет как есть; менять его — подсистема 2.

Установка Лидии закреплена на `94e038e` и не меняется, пока она не обновится сама.

## 9. Тестирование

Каждый новый тест сначала видим красным.

1. **Швы скиллов:** каждая команда и флаг из `SKILL.md` существуют в парсере CLI; для
   коннекторов — контрактные сценарии на подделке API: аргументы, результат, побочные
   эффекты, а не только наличие глагола.
2. **Швы хуков:** каждая запись `hooks.json` ↔ модуль в `h2t_ops/hooks/`.
3. **Ожидаемый вывод и бюджеты** каждого хука на каждом событии (§2.3, §2.4), без `jq` и
   системного Python, Linux и Windows.
4. **Обёртка:** нет CLI; CLI устарел (подделка, отвечающая кодом 5 на `--protocol`);
   CLI с протоколом; каталог `~/.h2t/run` недоступен на запись.
5. **Две комбинации версий** — функционально (§2.5).
6. **Старые данные:** fixtures сессий, спула, секретов в старых форматах и местах —
   читаются новым кодом так же, как старым.
7. **Wheel вне репозитория:** установка собранного пакета в пустой HOME (на Windows ещё
   `USERPROFILE`, `APPDATA`, каталоги uv), без чекаута и кэша плагинов — инструменты
   находят ресурсы.
8. **Детерминированность:** две установки тега → одинаковый `uv pip freeze` (§2.2).
9. **Сбой обновления:** ввод сбоя после каждого шага `update` → рабочая установка жива
   (§2.6); base → `[ocr]` → update → OCR на месте.
10. **Ratchet** по карте E0 и по литералам автора.

Живая приёмка — матрица §4 на настоящих машинах: macOS и Windows × Claude Code и Codex.

## 11. Вне рамок — следующие подсистемы

1. **Эта спека** — код и доставка.

4. **Система пользователя** — daily brief, задачи, POS как надстройка.

## 12. Отбраковано

- «Плагин без CLI работает частично» как довод против A: 12 из 26 скиллов уже падают без
  CLI, и падают молча; A делает зависимость явной, а не создаёт её.
- Переименование модуля `h2t_ops` и дистрибутива: польза косметическая, цена —
  снос рабочей установки при замене.
- Собственная чистка кэша плагинов в `update`: файлы старой версии может держать
  открытая сессия.
- «В `plugins/` останется только Markdown»: остаются данные-ресурсы скиллов и обёртка
  хуков; критерий — ноль исполняемого Python.

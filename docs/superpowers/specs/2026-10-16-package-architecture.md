# Package architecture

Весь исполняемый код — в одном пакете со своим Python и закреплёнными зависимостями.
Плагины несут тексты, данные-ресурсы и обёртку хуков. **На машине всегда ровно одна
версия пака — текущий выпуск.** При расхождении h2t не работает в смеси, а называет одну
команду, `h2t-setup sync`, которая сводит машину к текущему выпуску из любого состояния.

Версия 5 с правками раунда 5, после пяти раундов adversarial-ревью Codex (журнал в §13). v4 ввела точное
равенство версий; v5 исправляет механизм `sync`.

Первая из четырёх подсистем переработки (§11). Связи: #541 (трекер установки),
[спека wizard'а](2026-10-14-setup-wizard.md).

## 1. Проблема — что измерено

Цель — пак готов к работе у незнакомого человека без помощи автора: репозиторий
публичный. Сейчас им с трудом пользуется и сам автор. Инвентарь 2026-10-16 (субагент,
только чтение, `file:line`; четыре пункта перепроверены основной сессией):

- **Код в двух-трёх копиях.** Общая библиотека: `lib/`, ручная копия
  `plugins/h2t-core/lib/` и замороженная при сборке `h2t_ops/_plugin_payload/`.
  Коннекторы drive, meetgeek, research написаны дважды (~5100 строк на обе версии). Поиск
  файла секретов — в 6–7 местах. Установка и диагностика — в трёх местах.
- **Два канала исполнения одного кода.** Девять точек входа CLI — загрузчики скриптов
  плагина через лестницу из пяти путей (`plugin_entrypoints.py:1-22`). В кэше h2t-core
  3.2.61 — 55 файлов `.py` без Python и зависимостей: отсюда резолвер, заглушка Store,
  `uv run` за 0,9 с (D9), `jq` (D1).
- **Каналы обновляются независимо и расходятся молча.** Плагин — `/plugin marketplace
  update`, CLI — `uv tool install`. На машине автора: плагин 3.2.61, CLI 0.2.1. Каждый
  мерж в main сразу уходит всем, кто следит за marketplace: выпуска как события нет.
- **Личное автора в поставке.** ID базы задач Notion (`notion/commands.py:65`),
  `Asia/Jerusalem` в пяти местах, `Projects/DOR|Projects/newsengine`
  (`detect_project.py:35`). Идентификаторы, не секреты, но поведение у другого человека
  неверное.
- **Старые версии плагинов копятся.** Claude Code их не удаляет: семь версий h2t-core на
  машине автора.

## 2. Цель и критерии успеха

1. **Одна реализация** общей библиотеки, каждого коннектора, поиска секретов, doctor.
2. **Ноль runtime-Python в выпускаемых плагинах**; allowlist постоянных файлов:
   `hooks/run`. Ratchet по выпускаемым артефактам.
3. **Одна версия на машине.** После `h2t-setup sync` CLI и все управляемые плагины
   (§7.3) — версии текущего выпуска; это проверено запуском, а не записью в файле. Тест
   на изолированных конфигах.
4. **Расхождение никогда не молчит и никогда не шумит:** при любой смеси — одна строка
   на `SessionStart` с командой; на остальных событиях хуки h2t ничего не делают и не
   печатают. Скилл в любом харнессе первой командой видит расхождение и показывает ту же
   команду.
5. **`sync` сходится из любого состояния:** чистая машина; CLI 3.x; CLI новее или
   старше плагинов; повреждённое окружение CLI; прерванная установка; marketplace
   отсутствует. Повтор после сбоя доводит до цели. Тест вводит сбой после каждого шага.
6. **Детерминированная установка:** для фиксированной тройки «ОС, архитектура, extras»
   две установки одного выпуска дают один Python и один набор пакетов. Проба
   2026-10-16 на macOS: две установки wheel с `--python 3.12.11 --managed-python` и
   constraints из `uv.lock` в разные каталоги — одинаковые 51 пакет.
7. **Бюджеты по событиям** (тёплый запуск, p95, 20 прогонов, macOS и Windows):

   | Событие | Бюджет | Python |
   |---|---|---|
   | `UserPromptSubmit`, обычное сообщение | 50 мс macOS / 80 мс Windows | не запускается |
   | `UserPromptSubmit`, слэш-команда session-скилла | 3 с | gather |
   | `Stop` (оба хука) | 300 мс macOS / 400 мс Windows | да |
   | `PostToolUse` | 150 мс | только если хуку есть что делать |
   | `SessionStart` | 1 с | да |

   Пороги Windows — по пробе 2026-10-17 (§10, отчёт проб). `UserPromptSubmit` без
   Python: 56–62 мс, почти всё — старт bash в Git Bash; обёрткой это не сократить.
   `Stop`: одна цепочка обёртка → `h2t-hook.exe` тепло до 229 мс, холодно до 313 мс.
   Оба хука `Stop` харнесс запускает параллельно (документация Claude Code, не замер).

8. **Ожидаемый вывод** каждого хука на каждом событии записан и сверяется тестом.
9. **Литералы автора не прибавляются**; до нуля их доводит подсистема 2.

## 3. Принятые решения

| Вопрос | Решение | Отвергнуто |
|---|---|---|
| Где код | **A**: весь Python в пакете | B как общий подход — 0,9 с на Stop-хук на Windows (D9); допустим для отдельного инструмента только по замеру. C — два канала остаются |
| Совместимость | **Точное равенство** версий плагинов и CLI | окно N/N−1 (v3): четыре P1 раунда 3 — механизмы окна |
| Цель `sync` | **Только текущий выпуск.** Откат на старый — ручная установка из тега или чекаут | `sync <ver>` к любой версии: плагины из marketplace на main всё равно приходят текущими (раунд 4, B1) |
| Указатель выпуска | `marketplace.json` на main: каждый плагин — `git-subdir` с `ref` = тег и `sha` = коммит тега. Пишет только workflow выпуска | закрепление всего marketplace на `#<тег>`: сдвиг — только `remove` → `add`, а `remove` удаляет плагины (проба) |
| CLI | **wheel выпуска** из GitHub Release; точный Python uv-managed; constraints из `uv.lock` | установка из исходников: сборка, `hatchling` и его цепочка, git |
| Исполнитель `sync` | всегда версии **цели**: любой стартовый `sync` читает манифест цели и перезапускает себя её бутстрапом (§7.3) | исполнитель версии плагина, написавшего команду (раунд 4, B6) |
| Разработка | на main; без выпуска пользователи её не видят; автор работает с плагинами из чекаута | каждый мерж сразу у всех |
| Codex в `sync` | **не управляется в первом выпуске**: скиллы и CLI работают, плагины ставятся одной документированной командой; `sync` о них сообщает | управлять без проверенного способа доставки |
| Имя дистрибутива | остаётся `h2t-ops`; граница в `CLAUDE.md`: `h2t-ops` — весь пак | переименование: замена сносит рабочую установку |
| Старые версии плагинов | `sync` хранит две последние на плагин | не чистить; чистить всё, кроме текущей |
| Интерфейс | команды на PATH с `--json` | MCP-сервер |

## 5. Что где лежит

```text
h2t_ops/                       пакет — единственное место исполняемого кода
  core/         пути, секреты, конфиг, чтение JSON, ошибки, конверт ответа
  lifecycle/    gather, handoff, activity, eval
  hooks/        по модулю на хук
  connectors/   по одной реализации на коннектор
  setup/        wizard, sync, update, dev-sync
  tools/        docs-lint, drawio, сборщик creative
  resources/    данные инструментов (шаблоны creative, defaults drawio, known_secrets),
                importlib.resources
  cli.py        точки входа

plugins/<name>/
  skills/<skill>/SKILL.md, references/*.md
  hooks/hooks.json             "command": "bash \"${CLAUDE_PLUGIN_ROOT}/hooks/run\" <hook>",
                               "timeout": <секунды на хук>
  hooks/run                    обёртка, §6.1
  release.env                  VERSION=4.1.0 — пишет скрипт выпуска

release.json                   манифест выпуска в корне, на теге (§7.1)
```

Ресурсы, которые инструмент ищет рядом с собой (`assembler.py:12`, drawio
`config/defaults.yaml`), переезжают в `h2t_ops/resources/`. Проверка — wheel вне
репозитория и вне кэша плагинов (§9).

## 6. Контракты

### 6.1 Обёртка `hooks/run`

Только bash и чтение двух однострочных-по-ключу файлов. Python не запускается, пока
хуку нечего делать.

1. **Предфильтр** `UserPromptSubmit`: есть ли слэш-команда session-скилла. Нет — exit 0.
2. **Прочитать** `VERSION` из `${CLAUDE_PLUGIN_ROOT}/release.env` и проекцию установки
   `~/.h2t/run/install.env` (§6.4). Файл отсутствует, строка не вида `KEY=value`,
   `STATE` ≠ `ready` — установка считается отсутствующей.
3. **Решить** — строки проверяются сверху вниз, первая совпавшая решает:

   | Состояние | Действие |
   |---|---|
   | установки нет | уведомление «CLI не установлен» |
   | `EDITABLE_ROOT` задан, `${CLAUDE_PLUGIN_ROOT}` внутри него | запустить обработчик без сравнения: плагин и CLI из одного чекаута |
   | `EDITABLE_ROOT` задан, плагин вне его | уведомление «CLI в режиме разработки, плагины из marketplace» — даже при равных номерах |
   | `VERSION` равны | запустить `"$H2T_HOOK" <name>` дочерним процессом (ниже) |
   | `VERSION` различаются | уведомление «версии разошлись» |

   Сравнение — только на равенство: направление расхождения обёртке не нужно, цель
   `sync` всегда одна (§7.3).
4. **Запуск обработчика** — дочерний процесс, не `exec`: stdout и stderr во временные
   файлы, код выхода сохраняется. **Внутренний таймаут** — на 1 с короче поля `timeout`
   записи в `hooks.json` (сторож на bash: фоновый `sleep` + `kill`). Таймаут харнесса
   отбрасывает весь вывод хука, поэтому обёртка должна успеть раньше; сработавший
   внутренний таймаут обрабатывается как «иное» ниже. По коду:
   - 0 — stdout передаётся харнессу;
   - 2 — намеренная блокировка: stderr и код передаются как есть. Ошибки разбора
     аргументов CLI возвращают 64, не 2;
   - иное — вывод отбрасывается, строка в `~/.h2t/logs/hooks.jsonl`; на `SessionStart`
     — уведомление «CLI неисправен»; на остальных событиях — exit 0.
5. **Уведомление** — только на `SessionStart`, каналом `systemMessage`, один раз на
   `session_id` (метка создаётся `mkdir`, атомарно). Каталог недоступен на запись —
   на каждом `SessionStart`, включая resume и compaction. JSON — готовый литерал.

Команда в уведомлении — бутстрап выпуска, который собрал этот плагин (§7.2); он сам
находит текущий выпуск. Нет `uv` — строка установки `uv` для платформы.

### 6.2 Обработчик `h2t-hook <name>`

- читает stdin байтами и декодирует явно (`errors="replace"`);
- выбирает канал по событию одним эмиттером для всех путей выхода;
- при исключении — одна строка `h2t hook <name> failed: <класс>` в stderr, код 1,
  подробности в `~/.h2t/logs/hooks.jsonl`;
- модуль хука — чистая функция `handle(event: dict) -> Reply`.

### 6.3 Скиллы

- **Первая команда** каждого h2t-скилла: `h2t-ops version --expect <ver> --json`, `<ver>`
  — литерал скрипта выпуска. Команда проверяет не только себя: каждая точка входа из
  `install.json` находится через PATH харнесса и ведёт в тот же `tool_root`. Исходы,
  по порядку:
  1. валидный JSON с `ok: true` — продолжать;
  2. валидный JSON с `ok: false` — показать его `hint` (в том числе для
     `reason: path`, ниже);
  3. команда не найдена — сначала проверить, есть ли `~/.h2t/run/install.env` со
     `STATE=ready`: есть — это PATH, показать каталог `H2T_HOOK` из него и совет из
     пункта про PATH; нет — литерал бутстрапа (§7.2);
  4. всё остальное (ненулевой код без JSON, текст usage старого CLI) — литерал
     бутстрапа, вписанный выпуском.
- **PATH — отдельный исход.** Установка исправна, но PATH харнесса её не видит или видит
  другую (на Windows PATH обновляется только в новом окне). `sync` это не чинит: он не
  пишет в профиль оболочки (README). Поэтому `version --expect` различает этот случай и
  отвечает `ok: false, reason: path` с `hint`: каталог команд из `install.json`,
  «перезапусти харнесс» и `uv tool update-shell` как команду, которую человек решает
  выполнить сам. Хуки от PATH не зависят — они берут абсолютный путь из `install.env`.
- Дальше `SKILL.md` вызывает только команды CLI, всегда с `--json`; в каждой ошибке —
  `hint` с точной следующей командой.
- **Брифинг из хука** несёт строку `GATHER_META: <json>` — тот же JSON, что разбирает
  session-start 3.x, с двумя полями сверху: `cwd` (каталог, для которого собран брифинг)
  и `at` (время сборки, ISO-8601 со смещением). Формат один: второй, текстовый, сломал бы
  разбор 3.x. Скилл использует брифинг, только если `cwd` равен текущему каталогу и `at`
  не старше 120 с; иначе зовёт `h2t-gather`.
- Тест: каждая команда и флаг из `SKILL.md` есть в парсере CLI той же версии.

### 6.4 Состояние установки

`~/.h2t/run/install.json` — для Python, `~/.h2t/run/install.env` — его проекция для bash.
Пишет только `h2t-setup` (`sync`, `dev-sync`); оба файла — временный файл + rename.

```json
{
  "state": "ready",
  "version": "4.1.0",
  "generation": "<uuid каждой записи>",
  "tool_root": "<каталог инструмента uv>",
  "entrypoints": {"h2t-hook": "<абсолютный путь>", "h2t-gather": "<…>"},
  "editable": null,
  "user_options": {"extras": ["ocr"], "with": []},
  "plugins": ["h2t-core", "h2t-ops"]
}
```

```text
STATE=ready
VERSION=4.1.0
GENERATION=<тот же uuid, что в install.json>
H2T_HOOK=C:/Users/<user>/.local/bin/h2t-hook.exe      ← прямые слеши, без кавычек
EDITABLE_ROOT=
```

- **`install.env` — точка фиксации.** Порядок записи: `install.env` с `STATE=updating`
  → замена CLI → проверка запуском → `install.json` → `install.env` с `STATE=ready`
  **последним**. Состояние считается `ready`, только если `install.env` говорит `ready`
  и его `GENERATION` равен `generation` в `install.json`. Любое другое сочетание,
  включая прерывание между двумя последними записями, — «установки нет».
- После **каждой** успешной проверки, в том числе когда переустановка не понадобилась,
  `sync` заново пишет обе проекции в этом порядке. Повтор `sync` поэтому всегда
  восстанавливает согласованное состояние.
- Файлы — запись последней проверки, а не доказательство: `sync` всегда проверяет
  установку заново (§7.3.4).
- Пути — из `uv tool dir` и `uv-receipt.toml` в момент установки.
- `plugins` — набор, которым управляет `sync`. Пишет wizard; иначе — установленные
  плагины marketplace `lichtpfad`; иначе — `h2t-core`, `h2t-ops`.
- Нет `install.json`, но есть старая установка — `user_options` берутся из её receipt.

## 7. Выпуск и синхронизация

### 7.1 Выпуск

Один workflow выпуска, `concurrency: release` — выпуски не идут параллельно.

1. Скрипт выпуска на коммите выпуска ставит `<ver>` в `pyproject.toml`, все
   `plugin.json`, все `release.env`, литералы `--expect` и бутстрапа в `SKILL.md` и
   `hooks/run`; экспортирует `constraints.txt` (`uv export --frozen --no-dev --all-extras
   --no-emit-project --no-hashes`); пишет `release.json`:

   ```json
   {"format": 1, "version": "4.1.0", "previous": "4.0.0", "python": "3.12.11",
    "wheel": "<URL wheel в Release>", "constraints": "<URL constraints.txt в Release>",
    "bootstrap": ["uvx", "--isolated", "--python", "3.12.11", "--managed-python",
                  "-c", "<constraints>", "--from", "h2t-ops @ <wheel>", "h2t-setup"]}
   ```
   Один `CHANGELOG.md`; тег `v<ver>`.
2. CI на тег собирает wheel, прикладывает wheel и `constraints.txt` к GitHub Release,
   прогоняет тесты §9 на установленном wheel.
3. Только после этого — коммит на main, сдвигающий указатель (`marketplace.json`):

   ```json
   {"name": "h2t-core",
    "source": {"source": "git-subdir",
               "url": "https://github.com/lichtpfad/h2t-skills.git",
               "path": "plugins/h2t-core", "ref": "v4.1.0", "sha": "<40 знаков>"}}
   ```
   Сдвиг выполняется, только если текущий указатель равен `previous` из манифеста. Иначе
   workflow падает: указатель не откатывается назад.

Проба 2026-10-16: `git-subdir`, закреплённый на `v2.15.0`, ставит плагин 3.2.3; смена
закрепления + `plugin update` поднимает до 3.2.62 без `remove`, сохраняя scope и
выключенное состояние. Сокращение `owner/repo` в `url` ушло в SSH и упало — нужен полный
HTTPS-адрес. Документация: обновление приходит, только если меняется версия плагина; при
одной версии на выпуск она меняется всегда.

### 7.2 Бутстрап — одна команда для человека и агента

```bash
uvx --isolated --python 3.12.11 --managed-python -c "<constraints>" --from "h2t-ops @ <wheel>" h2t-setup sync
```

— это поле `bootstrap` манифеста любого выпуска плюс режим (`sync` или `update`).
`--isolated` обязателен: без него `uvx` может взять уже установленный инструмент — то
самое окружение, которое `sync` будет заменять. README и wizard дают его для текущего
выпуска; плагин и скиллы несут бутстрап своего выпуска. Какой бы ни запустили, он
приведёт к текущему (§7.3.1).

### 7.3 `h2t-setup sync`

1. **Цель.** Читает `marketplace.json` с main (raw GitHub), берёт тег из `ref` записи
   h2t-core, читает `release.json` этого тега. Сеть недоступна — стоп с причиной, ничего
   не тронуто.
2. **Исполнитель цели, изолированный.** Исполнитель продолжает, только если
   одновременно: его версия = цели, и он запущен не из окружения установленного CLI
   (`sys.prefix` не лежит в `tool_root`). Иначе — перезапуск командой `bootstrap` из
   манифеста цели **с тем же режимом и аргументами**: `update` остаётся `update`, а
   подтверждение, полученное до перезапуска, к цели не переносится — исполнитель цели
   спрашивает о своей версии сам. Установленный `h2t-setup sync`, запущенный для
   ремонта, тоже уходит в изолированный `uvx`. Контракт, который должен знать
   исполнитель любой версии, заморожен: поля `format`, `version`, `bootstrap` манифеста,
   правило «тег из `ref` h2t-core» и передача режима последним аргументом.
3. **Снимок** в `~/.h2t/run/rollback/<время>/`: `install.json`, `uv-receipt.toml`,
   версии, scope и enabled/disabled плагинов в каждом харнессе.
4. **CLI — проверка по факту:** запустить каждую точку входа из `install.json` с
   `--version`, импортировать модули выбранных extras python'ом окружения. Всё совпало с
   целью — пропуск. Иначе: `state=updating` → `uv tool install --reinstall --python
   <python> --managed-python -c <constraints> "h2t-ops[<extras>] @ <wheel>"` (+`--with`
   из `user_options`) → та же проверка → `state=ready`, запись `install.json` и
   `install.env`.
5. **Плагины в Claude Code** (если `claude` найден):
   - marketplace `lichtpfad` отсутствует → `claude plugin marketplace add
     lichtpfad/h2t-skills --json`; есть и следит за основной веткой → `claude plugin
     marketplace update lichtpfad`;
   - есть, но **закреплён** на ref (`ref` в `known_marketplaces.json`): `marketplace
     update` к текущему указателю его не приведёт, а перезакрепление — `remove` → `add`,
     и `remove` удаляет плагины. Поэтому `sync` останавливается на этом харнессе, ничего
     не меняет и показывает, на что закреплено, и точные команды: `remove`, `add` без
     ref, `install` каждого плагина набора с его scope из снимка. В режиме `update` —
     спрашивает «да?» и выполняет их сам, с восстановлением из снимка при сбое
     между командами;
   - для каждого плагина из `plugins`: не установлен → `claude plugin install
     <плагин>@lichtpfad --scope user`; версия ≠ цели → `claude plugin update`;
   - проверка: каждый плагин набора установлен и имеет версию цели. Пустой набор —
     ошибка, не успех.
6. **Codex** (если `codex` найден): не трогает; отчёт называет команду установки
   плагинов вручную для текущего выпуска.
7. **Чистка кэша плагинов Claude Code:** две последние версии на плагин остаются.
8. **Отчёт:** что приведено к цели; что не удалось и команда повтора — та же `sync`;
   открытым сессиям нужен `/reload-plugins` или новая сессия; сессиям старше двух
   выпусков — обязательно (их файлы могли быть удалены шагом 7).

Сходимость: каждый шаг сравнивает факт с целью и пропускает совпавшее; повтор продолжает
с несовпавшего. Сбой разрешения зависимостей на шаге 4 оставляет прежний CLI рабочим
(проба 2026-10-16); прерывание посреди замены оставляет `state=updating` — обёртка и
`sync` считают установку отсутствующей, повтор переустанавливает. Исполнитель всегда
работает из `uvx`, а не из повреждённого окружения.

`h2t-setup update` = `sync` с показом «было → станет» и CHANGELOG и вопросом «да?» до
шага 4.

### 7.4 Чекаут разработчика

Плагины автор грузит из чекаута (`claude --plugin-dir plugins/<name>`;
`scripts/claude-dev.ps1`). `h2t-setup dev-sync` ставит editable CLI с constraints из
чекаута и `user_options` из `install.json`, пишет `EDITABLE_ROOT`; Git не трогает.
Исключение из сравнения — только для плагинов внутри `EDITABLE_ROOT` (§6.1); плагины из
marketplace при editable CLI видят расхождение и получают уведомление. Скиллы из
чекаута проходят первую проверку, потому что версия чекаута одна для плагинов и CLI.
`sync` и `update` чекаут не трогают: при `EDITABLE_ROOT` они сообщают о нём и
останавливаются.

   Windows-путь в `H2T_HOOK`.

# Setup wizard

Одна команда от пустой машины до проверенных коннекторов. Программа держит шаги и
состояние; агент ведёт по ней пользователя по протоколу; секреты не проходят через чат.

Связи: #534 (выбор коннекторов), #536 (Dropbox), #532 (google auth), #452 (Codex), #533.

## 1. Проблема — что измерено

Первая передача пака внешнему пользователю (2026-10-14, Codex) прошла через три разных
входа и ручную сборку инструкции. Измерено в тот же день, в пустом HOME и изолированном
`CODEX_HOME`:

- **Нет единого входа.** Плагины ставятся слэш-командами (Claude Code) или
  `codex plugin add` (Codex), CLI — `uv tool install`, настройка — скиллом
  `h2t-core:setup`, который сам приезжает только с плагинами.
- **Setup — инструкция для агента, а не программа.** `SKILL.md` перечисляет вызовы
  `setup_h2t.py`; что именно агент скажет пользователю, решает агент. Агент пользователя
  пересказал шаги Google как «подготовь credentials.json», выбросив создание клиента,
  включение API и consent screen.
- **Коннекторы покрыты неравномерно.** Google — одной командой (`h2t-ops google auth`,
  #532). Ключи — пустыми строками `KEY=` в файле, правка руками. Telegram — отдельный
  поток. Dropbox setup не знает вовсе (#536). Выбрать подмножество нельзя: всё, что не
  настроено, — `missing` (#534).
- **Секреты идут через чат.** Код входа Telegram и пароль 2FA передаются агенту и уходят
  в `--code` / `--password` командной строки: в транскрипт и историю оболочки.
- **«Установлено» утверждается до проверки.** Инструкция говорила агенту, что пакет
  установлен, до того как проверки прошли.
- **В Codex setup не проверен.** Песочница может не дать сеть и запись в `~`.

## 2. Цель и критерии успеха

Человек с нуля запускает одну команду, его агент (Claude Code или Codex) ведёт его по
шагам, и в конце каждый **выбранный** коннектор подтверждён живым запросом на чтение.

Успех измеряется так:

1. На чистом пользователе macOS одна команда → все выбранные коннекторы `verified`.
2. То же под Codex.
3. Ни одно значение секрета не появляется ни в одном выводе программы, в состоянии, в
   логах (тест 3, §8).
4. Повторный запуск не спрашивает ничего, что уже работает.
5. Пропущенный коннектор в отчёте — «не настроен», а не «сломан».

## 3. Принятые решения

| Вопрос | Решение | Отвергнуто |
|---|---|---|
| Кто ведёт | **Гибрид**: программа держит шаги, агент ведёт по протоколу, показывая тексты шагов дословно | только агент (зависит от харнесса, импровизирует); только TTY-программа (агент не может её вести) |
| Секреты | **Локальная страница** `127.0.0.1` с одноразовым токеном; запасной путь — скрытый ввод в терминале | через чат (транскрипт, провайдер модели) |
| Вход | **Одна команда с нуля**: `uvx --from git+…@<коммит> h2t-setup` | wizard внутри уже установленного пака (первые два шага остаются ручными) |
| Движок | **Модуль `h2t_ops/setup/` + команда `h2t-setup`** | расширить `setup_h2t.py` (живёт в плагине — появляется после установки); MCP-сервер (сам требует установки и конфига) |

## 4. Архитектура

Новый модуль `h2t_ops/setup/`, десятая точка входа `h2t-setup` в `pyproject.toml`.
Логика `setup_h2t.py` (doctor, установка, проверка коннекторов) переезжает в модуль;
скрипт остаётся тонкой обёрткой для обратной совместимости. Скилл `h2t-core:setup`
становится протоколом ведения `h2t-setup`.

Каждый шаг — три функции:

```text
check()        → done | pending | blocked(reason)   только читает машину
present()      → объект шага                         что сказать, куда отправить
apply(answer)  → действие, затем снова check()
```

Порядок шагов:

```text
env       uv, Python ≥ 3.11, найденные харнессы (claude, codex)
cli       h2t-ops на PATH, версия = закреплённый коммит
plugins   marketplace + h2t-core, h2t-ops в каждом найденном харнессе
select    выбор коннекторов
<card>×N  шаги карточки каждого выбранного коннектора (§5)
verify    живая проверка каждого выбранного
report    что работает, что пропущено, что не прошло
```

Плагины ставит сама программа: `claude plugin marketplace add` / `claude plugin install
--json` и `codex plugin marketplace add <repo>@<ref>` / `codex plugin add --json` (оба
CLI существуют, проверено 2026-10-14).

### Протокол для агента

```bash
h2t-setup next --json                    # первый незавершённый шаг
h2t-setup answer <step> <value> --json   # ответ на question / auto
h2t-setup status --json                  # все шаги и их состояние
```

Объект шага:

```json
{
  "step": "connector.google.client",
  "kind": "user_action",
  "say": "…",
  "instructions": ["…"],
  "ask": null,
  "secret_url": null,
  "then": "…"
}
```

| `kind` | агент |
|---|---|
| `question` | задаёт вопрос из `ask` с вариантами, передаёт ответ через `answer` |
| `user_action` | показывает `instructions` дословно, ждёт «готово», вызывает `next` |
| `secret` | даёт ссылку `secret_url`; значение не видит |
| `auto` | выполняет через `answer`; для сети и записи в `~` заранее предупреждает о запросе выхода из песочницы |
| `done` | показывает отчёт |

Выполненность шага решает только `check()`. Агент не утверждает «сделано».

Без аргументов `h2t-setup` проходит те же шаги интерактивно в терминале.

## 5. Карточки коннекторов

Данные, а не код: `h2t_ops/setup/cards/<name>.yaml`. Карточки поглощают
`known_secrets.yaml` — у описаний и ссылок ключей один дом; подсказки в ошибках
коннекторов (`hint=`) берут текст оттуда же.

```yaml
name: notion
title: Notion
pitch: "Страницы и базы Notion"
needs:
  - secret: NOTION_API_TOKEN
    validator: "starts_with:secret_"
how:
  - "Открой https://www.notion.so/profile/integrations → New integration"
  - "Тип Internal, выбери workspace → скопируй Internal Integration Secret"
  - "В Notion открой нужные страницы → ••• → Connections → добавь интеграцию"
verify: ["notion", "search-workspace", "--limit", "1", "--json"]
cost: free
```

| Карточка | От человека | Шаги | Живая проверка |
|---|---|---|---|
| google (Gmail, Calendar, Drive) | свой OAuth-клиент Desktop | `user_action` Cloud Console, три API, consent screen с объяснением Testing/Test users против In production → `secret` **загрузить скачанный JSON через страницу** (перетащить файл в форму; программа сама кладёт его в `~/.config/google-calendar-mcp/credentials.json`) → `auto` `h2t-ops google auth` | `gmail list --max 1`, `calendar list --max 1`, `drive folders` |
| telegram | api_id/api_hash; телефон с уже залогиненным Telegram | `secret` api_id+api_hash → **вход по QR на странице** (сканировать телефоном: Настройки → Устройства → Подключить устройство), пароль 2FA — полем на той же странице. Запасной путь — код: канал доставки показывается человеку (`SentCodeTypeApp` → «ищи в приложении»), `SetUpEmailRequired` и `SEND_CODE_UNAVAILABLE` — явные ошибки, а не «код запрошен» | `telegram auth status`, `telegram dialogs --limit 1` |
| dropbox | приложение в App Console | `user_action` создать app → `secret` app key/secret → `user_action` URL авторизации → `secret` код → обмен на refresh-токен | `dropbox account` |
| notion | integration token, подключённые страницы | `user_action` + `secret` | `notion search-workspace --limit 1` |
| meetgeek | API key | `user_action` + `secret` | `meetgeek auth-check` |
| granola | API key | `user_action` + `secret` | `granola auth-check` |
| research | Exa API key | `user_action` + `secret` | `research preflight`; живой платный запрос — только с согласия |

Сбой проверки: шаг не выполнен; `present()` показывает класс ошибки и подсказку
коннектора и предлагает «повторить» или «пропустить». Пропуск пишется в состояние.

Изменения в коннекторах, которых требуют карточки:

- telegram: код и пароль 2FA принимаются не аргументом командной строки (stdin или
  вызов из процесса страницы секретов);
- dropbox: обмен кода авторизации на refresh-токен (#536).

## 6. Страница секретов

Шаг `secret` запускает фоновый процесс-сервер и возвращает его адрес; `next` при этом
завершается. Сервер:

- слушает только `127.0.0.1`, случайный порт;
- отвечает только по пути с одноразовым случайным токеном, иначе 404;
- проверяет заголовок `Host`;
- после одной успешной отправки завершается; без отправки — через 15 минут, и `next`
  выдаёт новый адрес;
- показывает ту же инструкцию «где взять», что карточка;
- проверяет формат валидатором карточки; при ошибке показывает причину и ничего не пишет;
- никогда не возвращает значение — ни на страницу, ни в JSON, ни в лог. Агент видит
  `set` или `invalid_format`.

| Секрет | Куда |
|---|---|
| API-ключи, Dropbox app key/secret | `~/.h2t/config/secrets/secrets.env`, атомарно, права 600 |
| Telegram api_id/api_hash | `~/.config/telegram/config.json` |
| код Telegram, пароль 2FA, код авторизации Dropbox | никуда: сервер сам выполняет действие и пишет в состояние только результат |

Страница умеет три вида полей: текст (ключ), **файл** (перетащить скачанный JSON —
браузер читает «Загрузки», терминал нет, §12) и **QR** (картинка для входа в Telegram,
обновляется сама, пока не отсканирована).

Запасной путь — `h2t-setup secret <card>`: скрытый ввод (getpass), то же сохранение.
`next` предлагает его, если сервер не поднялся.

## 7. Состояние, повтор, обновление

Истина — машина. `~/.h2t/setup/state.json` хранит только то, чего из машины не вычитать:

```json
{
  "pin": "<sha>",
  "harnesses": ["codex"],
  "selected": ["google", "telegram"],
  "skipped": {"dropbox": "user declined"},
  "verified": {"google": {"ok": true, "at": "…"}}
}
```

Без секретов. Удаление файла теряет выбор и историю проверок, не сделанное.

- Повторный запуск продолжает с первого незавершённого шага; живые запросы — только для
  непроверенных или по `--reverify`.
- `h2t-setup add <card>`, `h2t-setup select`, `h2t-setup status`.
- Снять выбор — перестать проверять. Ключи из файлов wizard не удаляет.
- Обновление — только явное: `h2t-setup update` показывает «было <pin> → станет <sha>» и
  список изменений, после «да» переставляет CLI и плагины и повторяет проверки.
- Существующие установки: ключи в `~/.dor/…` коннекторы читают, `check()` засчитывает
  шаг выполненным. Ничего не переносится.
- Блокировка в `~/.h2t/setup/`: второй одновременный запуск получает `blocked`.
- Состояние у каждой машины своё, не синхронизируется.

## 8. Тестирование

Каждый новый тест сначала видим красным.

1. **Шаги без сети.** HOME и USERPROFILE во временную папку; `uv`, `claude`, `codex`,
   `h2t-ops` — записывающая подделка. Проверяются вызовы и то, что `check()` видит
   результат.
2. **Швы.** Каждая команда `verify` из карточек существует в парсере `h2t-ops`;
   подсказки коннекторов совпадают с карточками; каждый объект шага соответствует схеме.
3. **Секреты не утекают.** Прогон всего wizard'а с секретом известного уникального
   значения; поиск значения во всех выводах `next`/`answer`, в `state.json`, логах →
   0 совпадений. Контроль: значение находится в `secrets.env`.
4. **Сервер секретов.** Без токена → 404; чужой `Host` → отказ; вторая отправка
   отклонена; таймаут выключает; значение не возвращается; права 600 только на POSIX.
5. **Сквозной прогон на реальных инструментах, изолированно.** `uvx` из локального
   коммита; настоящий `codex plugin add` в изолированный `CODEX_HOME`; настоящий
   `claude plugin install` в изолированный конфиг; коннекторы с фиктивными ключами →
   классифицированная ошибка, не «готово».

CI: Linux и Windows, все пути `evals.yml`, не только `tests/`.

### Живая приёмка (руками, настоящие аккаунты)

1. Ноутбук, чистый пользователь macOS, агент Claude Code: одна команда → все карточки.
2. То же в Codex.
3. Вход в Google через браузер (до сих пор ни разу не проходил вживую).
4. Код Telegram через страницу, с 2FA.
5. Первый внешний пользователь; его баги — через `h2t-core:report-issue`.

## 9. Проверить до плана

Каждый пункт — одна проба, результат меняет план:

- слушает ли песочница Codex порт на `127.0.0.1` — если нет, в Codex по умолчанию
  запасной путь;
- можно ли изолировать `claude plugin install` (`CLAUDE_CONFIG_DIR`) для теста 5;
- работает ли `uvx --from git+…@<sha> h2t-setup` с тяжёлыми зависимостями за разумное
  время — 404 МБ окружения, из них ~250 МБ OCR (`rapidocr-onnxruntime`), нужного одной
  функции research; кандидат в extra.

## 10. Вне рамок

- удаление коннекторов вместе с ключами;
- синхронизация состояния между машинами;
- Linux-десктоп как отдельно проверяемая платформа;
- перенос старых установок с `~/.dor` на `~/.h2t`.

## 11. Отбраковано

- «Хуки h2t в Codex не работают» как общее утверждение — измерено только
  `plugin_hooks: removed` в Codex 0.159.2; формулировка в инструкциях: не рассчитывать
  на автоматический запуск хуков, вызывать скиллы явно.
- «Свой OAuth-клиент снимает 7-дневный лимит токена» — лимит зависит от режима
  приложения (Testing), а не от владельца клиента; политика Google не проверялась здесь.
- «Код Telegram иногда приходит на почту» как совет «проверь почту» — канал
  `SentCodeTypeEmailCode` в схеме есть (Telethon 1.42), но выбирает его Telegram; совет
  без знания канала — гадание. Отсюда требование R3.

## 12. Первая раскатка — что сломалось и что из этого следует

2026-10-14, внешний пользователь, macOS, Codex. Каждая строка — наблюдение и
требование к wizard'у, которое его закрывает.

| # | Что произошло | Требование |
|---|---|---|
| R1 | Код Telegram запрошен (`SentCodeTypeApp`), не найден ни в одном приложении; `auth.resendCode` → `SEND_CODE_UNAVAILABLE`. Вошли только по QR | Telegram: **QR — основной путь**, код — запасной (карточка §5) |
| R2 | `request-code` вернул `code_requested: true`, выбросив тип доставки — никто не знал, где искать | код-путь показывает канал доставки и маску почты; `SetUpEmailRequired` и `SEND_CODE_UNAVAILABLE` — ошибки с объяснением |
| R3 | Агент пользователя советовал «выйти из Telegram на телефоне и начать вход» — потеря сессии, куда приходят коды | тексты шагов только из карточек (§4); протокол запрещает агенту советы вне `instructions` |
| R4 | Многострочные блоки (`cat <<'PY'`) из чата ломались при вставке: незакрытый heredoc / `dquote>`, команды молча копились, «echo ничего не печатает» | человеку — **только однострочные команды**, никаких heredoc и вставки кода; файлы создаёт программа |
| R5 | Агент переписал присланный скрипт, и `__name__` стал `.name` — markdown съел подчёркивания | агент не перепечатывает код; всё, что исполняется, поставляется программой |
| R6 | `cp ~/Downloads/… → Operation not permitted`: у приложения терминала нет доступа macOS к «Загрузкам» | программа **не читает** `~/Downloads`, `~/Desktop`, `~/Documents`; файлы (Google JSON) принимаются через страницу, у браузера доступ есть |
| R7 | Агент Codex буквально исполнил «остановись на ошибке» и отказался от следующего шага | правила остановки живут в состоянии программы (`blocked` с причиной и следующим путём), а не в тексте для агента |
| R8 | Интерактивные шаги (QR, ожидание, скрытый пароль) агент выполнить не может | такие шаги — `kind: secret` на странице или `h2t-setup secret` в терминале человека, никогда не `auto` |
| R9 | Пользователь рапортовал `FILE OK`, которого не было — вывод длинный, строку легко пропустить | выполненность — только по `check()`; человеку не нужно читать вывод команд, чтобы понять результат |
